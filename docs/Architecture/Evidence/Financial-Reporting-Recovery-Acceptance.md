# Financial reporting recovery acceptance

Local Windows verification on 2026-10-03 covers Payment 10, Reporting 20/application compatibility 0.23.0 and existing Order 11. This evidence establishes the tested development scope, not production financial certification.

## Executed scope

- Full solution build: zero warnings/errors. Solution tests: 776 passed, 108 optional skipped (585 unit, 186 integration and 5 architecture passed).
- Twelve distinct opt-in live PostgreSQL/RabbitMQ cases passed without skips: four `FinancialCompletenessPipelineTests`, one Payment clean-database runner, one Reporting clean-database runner, three existing sale projection/replay cases, two existing Paid receipt/replay cases and one Payment readiness case. The final source-envelope hardening rerun passed all four pipeline and three sale projection cases.
- Refund publication rollback proves state/receipt/outbox/retention share the transaction. Original UUID/time survive outbox loss, replay is attributed, wrong tenant returns no candidates and conflicting/immutable evidence fails closed.
- Historical refunds retain a validated surviving original or report missing history without fabricating a new event ID.
- Combined reconciliation detects missing, conflicting and extra rows, independent sale/payment time bases, refund-before-sale delivery and immutable exact-scope observations. The final live-case rerun verifies that two distinct sub-microsecond request windows sharing one PostgreSQL timestamp bucket cannot retrieve one another's observation. Its live case also invokes the actual `FinancialReportingRecovery` executable with owning scoped connections and `--record`, verifying `observed_complete`, recorded output and omission of operator attribution. This is an assertion within the existing case, not an additional case.
- The actual hosted Reporting process consumes from isolated durable financial queues. A refused loopback broker endpoint leaves source outbox retry evidence; later publication succeeds. Refund precedes sale; the owned Reporting process is terminated, sale and duplicate refund queue during downtime, and a fresh process reaches observed completeness with one refund hash receipt and no refund dead letter.
- Payment's actual runner exercises the original 0→1→9→8→9 path plus 10→9→10 with empty retention, repository completion and refusal of 10→9 after publication. Reporting's runner exercises 0→20→19→20, refusal at sale history, re-upgrade after the safe preceding step, recorded observation and refusal of 20→19. Migration 10 readiness verification rejects a version-9 schema and accepts the required current version.

Fixtures use generated owning schemas/databases and exchange/queues and clean them afterward. They terminate only child processes created by the hosted test; they do not stop the shared broker. HTTP verification separately checks authentication, live sales permission, cross-branch/revoked denial, invalid periods, no-store and `not_checked`; its final failure case checks sanitized no-store 503 without restricted diagnostics.

## Limits and documentation

The hosted interruption is between completed refund projection and queued sale delivery. It does not prove the post-commit/pre-ack crash boundary or a full broker restart. Sources are separate observations rather than a distributed snapshot. Lost pre-ledger refund originals and historical Paid Orders without receipts remain gaps. No deployed restricted-credential grant verification, provider settlement, global certification, manual refunds, return/restock, fiscal credit notes, portal completeness UI or production release sign-off is included.

Behavior is documented in the [API contract](../../API/Financial-Reporting-Completeness.md), [runbook](../../Deployment/Financial-Reporting-Recovery.md), [ADR-019](../Decisions/ADR-019-scoped-financial-completeness.md), recovery tool/component READMEs, Database Design, root README and both architecture summaries. The Restaurant POS architecture also reflects this scope. Verification commands and environment opt-ins are in the runbook.
