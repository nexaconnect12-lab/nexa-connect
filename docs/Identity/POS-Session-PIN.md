# Windows POS session PIN unlock

The optional six-digit PIN unlocks only the same cashier's already authenticated, still-live session in the running Windows POS process. It is not a Keycloak password, staff-wide credential or offline sign-in method. Full OIDC/PKCE sign-in remains the identity authority. The staff UI always requests `prompt=login` on its full-sign-in path, including first sign-in and after local sign-out; PIN resume is a separate explicit action. See [ADR-064](../Architecture/Decisions/ADR-064-pos-session-pin-and-customer-panels.md) and [operator setup](../Deployment/POS-Cashier-Ready-And-Customer-Panels.md).

## Enrollment and resume

After successful full sign-in, a cashier may explicitly set/confirm exactly six ASCII digits within two minutes. Enrollment requires a live authenticated session and `Session:EnablePinUnlock=true` (default). There is no preset PIN. The verifier belongs to that process/session and is destroyed by successful full sign-in, sign-out, application disposal or five consecutive failed attempts. Re-enrollment requires another eligible full sign-in; restart cannot restore a PIN.

Manual and idle lock still persist the existing nonsecret locked identity marker and mask operational work. When eligible, they additionally suspend the unchanged token set privately in process memory; `CurrentToken` contains only the marker while locked. PIN verification requires matching original subject/authority, unexpired access token, original absolute deadline and no pending full sign-in. Successful verification saves/restores the original token set before reopening the workspace. It creates no token, refresh, role, grant, session extension or business command. APIs continue their normal live authorization.

Access/absolute expiry, rejected refresh, display-safety/security lock, restart, exhausted attempts or choosing full sign-in remove the quick-unlock capability and require the original full authentication flow. Cancellation, wrong identity or failed full sign-in leaves retained work protected. A PIN cannot refresh an expired access token or establish offline authority. Full sign-in may be needed sooner than the configured absolute timeout because the suspended access token can expire while locked.

## Credential handling and scope

`PosSessionPin` derives a 32-byte verifier using PBKDF2-HMAC-SHA256 with 600,000 iterations and a random 16-byte salt. Comparison is fixed-time; temporary derived bytes and disposed verifier/salt buffers are zeroed. The salt/verifier and suspended credentials are not added to SQLite, token files, recovery exports or a server credential registry. This uses the existing .NET cryptography implementation without a new dependency. The iteration choice follows [OWASP's PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); it is not a claim that a six-digit PIN is a strong standalone password, device attestation or FIPS certification. Windows/process access remains a prerequisite security boundary.

Successful/failed PIN events use the existing `nexaconnect-pos-client` session logger, with safe operation names such as `session-pin-enrolled`, `session-pin-denied`, `session-pin-resumed` and `workspace-locked`. They contain no PIN, verifier, token or credential body. No identity client, permission, server schema or API changes are introduced. The optional validated `preferred_username` comes from authenticated UserInfo for staff display only; subject/authority remain the identity binding.

**Switch cashier** requires no retained shift, cash session, cart, pending order/checkout/refund/review or unresolved outbox work. It delegates to guarded sign-out and full sign-in; it cannot transfer ownership of existing work. Fingerprint and RFID/card authentication remain unavailable pending an identified reader, supported SDK/protocol, enrollment proof and actual hardware/security verification. Merely connecting a keyboard-wedge reader does not authorize a cashier.
