# Administrative settlement replay contract

The executable accepts `--settlements` as its first switch. This is not an HTTP/customer capability. The existing protected settlement manifest, ledger, BFF and portal remain read-only. The CLI requires explicit organization/Restaurant/branch UUIDs, `--from-date` and `--to-date` in invariant `yyyy-MM-dd` (inclusive/exclusive), and `--limit 1..31`. Dates select the receipt's business date, not decision timestamp. Range is at most 31 dates, with an exclusive upper date no later than tomorrow in UTC, matching source inventory validation; only durable committed receipts can be selected. At most 1000 correction items and 2 MiB retained payloads are allowed. Overflow fails rather than truncating.

Default preview prints only `{mode:"preview",Manifest:"<SHA256>",Count:n}` and creates no audit or broker connection. The digest includes exact owning scope, dates, limit and EventId-sorted original event ID/version/raw UTF-8 payload hashes. Raw bytes are the stored outbox JSON representation returned by PostgreSQL, including retained property order/whitespace; they are forwarded without serializing replacement events. Financial/proof fields and source receipt/decision/aggregate/correlation/time/version must agree. Unknown publication fields are rejected rather than silently discarded.

`--execute --operator <UUID> --reason retry|rebuild --manifest <exact preview SHA256>` is mandatory for publication. Execution-only fields without `--execute`, duplicate/unknown arguments, invalid attribution/date/limits or malformed hashes are rejected. Execution reselects and validates its digest while creating the durable intent in the same owning transaction. A new commit or changed scope/limit/bytes invalidates the old selection. A successful result emits `{mode:"executed",runId:"<UUID>"}` and a safe broker-confirmation log; it does not claim delivery completeness.

Original V1 and V2 payloads retain IDs and schema. V1 remains historical proof unavailable; V2 includes original correction proof. No V1 upgrade, new UUID/correlation/time, repricing or redistribution of correction amounts is performed. Both queue bindings must exist. Original outbox flags and financial/settlement state stay unchanged, including for already-published rows. Replay broadcasts to all subscribers matching the selected routing keys.

Run audit stores scope/date/operator/reason/manifest/count/limit, selected IDs/version/payload hashes, actual database login and creation time; it stores no financial body. Attempt audit stores run/event/started-or-confirmed, login and time. Selection membership, started-before-confirmed and immutable history are enforced. The supplied operator UUID is asserted; SQL forces `session_user`, including if a caller supplies a forged login field.

Interruption returns exit 1 with a sanitized run UUID if execution began; the intent may be absent after a pre-write failure or present after an uncertain commit. Inspect audit rows. Started without confirmation is uncertain, not definitely unpublished; confirmed proves broker routing only. Make a fresh preview, execute a new run with original identities and reload the authorized settlement ledger. Exact duplicates do not change Reporting facts/checkpoints. Invalid/conflicting originals require investigation/restored legitimate history, not replacement IDs or overwrites. Exit 0 means preview completed or broker confirmations completed; help also returns 0. Invalid/unavailable/interrupted execution returns 1 without raw downstream errors or credentials.

No new HTTP schema or permission is added. Shared observability emits `nexaconnect-settlement-replay` structured JSON/optional OTLP and original correlation scopes. See [operations](../Deployment/Settlement-Replay.md) and [ADR-035](../Architecture/Decisions/ADR-035-audited-settlement-replay.md).
