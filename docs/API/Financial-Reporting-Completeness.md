# Scoped financial reporting completeness

Payment 10 and Reporting 20 (minimum application 0.23.0), with Order 11, add original refund-event retention, attributed replay and combined sales/payment/refund reconciliation. This is a bounded observation of available source evidence, not a financial certification or durable completeness watermark. See [ADR-019](../Architecture/Decisions/ADR-019-scoped-financial-completeness.md) and the [recovery runbook](../Deployment/Financial-Reporting-Recovery.md).

## Evidence and time boundaries

Payment commits the original `payment.refunded.v1` payload in immutable `refund_financial_publications` together with completion, receipt, audit and outbox state. Refund event UUIDs remain the originally generated UUIDs. Replay can retain a pre-migration original surviving in the outbox after validating it against the immutable receipt. An older refund whose original event has been lost remains an evidence gap; no replacement event UUID is invented.

Order's combined manifest includes receipt-backed Paid Orders whose original creation time **or** receipt Paid time intersects the selected half-open UTC window. It checks both corresponding facts even if one time falls outside that window. Refund candidates use completion time. Historical Paid Orders without receipts, invalid or conflicting retained evidence, and unretained originals are explicit gaps. The older standalone sale tool still selects receipt-Paid windows.

The checker compares original source evidence against one repeatable-read Reporting snapshot. Sales, payments and refunds independently count expected, matched, missing, conflicting and unexpected rows. It verifies event/aggregate identity, tenant/restaurant/branch, method/origin, currency, amounts, original timestamps, fact versions and normalized event receipt hashes. Reporting inventory covers scoped rows in each fact's own time window and expected aggregate keys, so an expected row with incorrect scope or time is conflicting. Unexpected counts cover only the selected tenant/branch/time. No report totals, payment state or original sales are changed.

`observed_complete` requires all three inventories to match and source evidence gaps/unretained counts to be zero. Otherwise status is `gaps_detected`. The manifest hash identifies sorted source financial evidence and gap counts; source-read times and Reporting check time remain separate provenance. Operational databases are read separately, and late completion or subsequent projection changes can invalidate an earlier observation. Recheck after consumption catches up. This does not certify capture/settlement accounting, every historical source, item sales, cash-close totals, or production acceptance. Existing `netPaid` semantics remain unchanged.

## Read API

`GET /api/reporting/v1/customer/organizations/{organizationId}/reports/financial-completeness?branchId={uuid}&fromUtc={iso}&toUtc={iso}` returns the newest **recorded** observation for that exact organization, branch and window. All query values are required. The window must be positive, at most 31 days, and already closed (`toUtc <= now`). Responses are no-store.

Authentication, organization/product access and live `reporting.sales.read` authorization use the existing Reporting boundary on every request. Cross-scope denial returns 403; invalid inputs return 400. Unexpected authorization/database failures return a sanitized no-store 503 ProblemDetails response; logs record only permission and exception category. A dependency's explicit non-success authorization response denies access. No workload bypass or new permission is introduced. A missing record returns HTTP 200 with `{"status":"not_checked","observation":null}`. A record returns `status` and `observation` containing check UUID, range, source/check timestamps, manifest hash, source gap/unretained counts and separate `sales`, `payments`, `refunds` count groups (`expected`, `matched`, `missing`, `conflicting`, `unexpected`, `gaps`). Actor attribution stays in restricted persistence and is excluded from the API.

Reading the API does not run reconciliation or mark anything complete. The route is a direct Reporting API; this slice adds no Customer BFF forwarding route or portal completeness UI. Dashboard/sales totals and global checkpoint fields retain their previous contracts.

## Persistence and verification

Payment 10 owns immutable `refund_financial_publications`, append-only `refund_financial_replay_audit` and scope indexes. Reporting 20 owns append-only `financial_completeness_checks`, scoped/time-indexed result JSON with restricted operator attribution. Both migrations refuse downgrade after retained history exists. Recording is an explicit operator-tool operation; Reporting services never connect to Order or Payment databases.

Verify `FinancialCompletenessTests`, `FinancialCompletenessHttpTests`, `FinancialCompletenessPipelineTests`, `PaymentMigrationRunnerAcceptanceTests` and `SaleReportingMigrationAcceptanceTests`. See the runbook for opt-ins and the [acceptance record](../Architecture/Evidence/Financial-Reporting-Recovery-Acceptance.md) for the executed scope. Reporting uses service `nexaconnect-reporting`; query Loki `{service_name="nexaconnect-reporting"} |= "Customer reporting authorization denied"` or `|= "Customer reporting query failed"`, and inspect existing sale/refund consumer outcome metrics. Logs exclude financial payloads, amounts, actor identities and credentials. CLI output is a restricted operator result, not telemetry.
