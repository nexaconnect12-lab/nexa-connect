# Branch day-close preparation

The [joined preparation acceptance gate](../Deployment/Day-Close-Portal-Acceptance.md) implements actual Customer authentication and owning HTTP preparation/recovery verification. Synthetic source repository transitions are explicit fixture boundaries; eleven browser scenarios, six Authorization persistence cases and verified cleanup are required before recording a pass.

POS owns durable preparation for one organization, Restaurant-resolved branch and business date. Reporting remains a read-only source of reconciliation evidence. This workflow observes readiness for review; it does not approve settlement, lock a day, freeze source writes, run repair, publish a settlement event or prove a distributed financial cutoff. See [ADR-021](../Architecture/Decisions/ADR-021-branch-day-close-preparation.md) and [rollout](../Deployment/Day-Close-Preparation.md).

## Routes and authorization

| Route | Purpose |
| --- | --- |
| `GET /bff/customer/day-close-preparations?branchId={uuid}&businessDate=yyyy-MM-dd` | Load and freshly validate saved readiness |
| `GET /bff/customer/day-close-preparations/csrf` | Obtain the session antiforgery request token |
| `POST /bff/customer/day-close-preparations` | Prepare, refresh or explicitly resume an interrupted operation |
| `GET /api/pos/v1/customer/organizations/{organizationId}/day-close-preparations?branchId={uuid}&businessDate=yyyy-MM-dd` | Authorized owning API read |
| `POST /api/pos/v1/customer/organizations/{organizationId}/day-close-preparations` | Authorized owning API command |

POST accepts `{ "branchId": "uuid", "businessDate": "2026-09-01", "operationId": "uuid", "expectedVersion": 0, "reasonCode": "routine_close" }`. Only `routine_close` and `recheck` reasons are allowed; no freeform personal text. The BFF requires `X-Nexa-CSRF` from the CSRF response, an authenticated Customer session, matching protected tenant subject, current Directory membership and the NexaConnect product. It derives organization and bearer server-side; browser organization, actor, timezone and UTC parameters confer no authority. Commands are limited to 4096 bytes.

POS requires a customer role, exact live Restaurant organization/restaurant/branch hierarchy and a fresh Authorization decision on every read, command and replay. Authorization migration 10 grants `pos.day-close.read` to tenant-admin/store-manager/accountant and `pos.day-close.prepare` only to tenant-admin/store-manager, including new assignments. Read permission authorizes retained POS preparation evidence. Fresh capture/validation additionally needs Reporting `reporting.sales.read` and all existing [source read permissions](End-Of-Day-Draft.md). Preparation is not a financial approval, so no amount-limit decision is requested. Actor subject and decision UUID remain restricted in POS audit, never in the customer view. Authorization is a live observation, not a revocation lock spanning the later transaction.

## States, versions and recovery

A missing record returns `not_prepared`, version 0. Accepted prepare commits `preparing` and advances the version before HTTP evidence reads. Completion advances the version again to `blocked` or `ready_for_review`. The response contains exact `identity`, `version`, `status`, nullable frozen `snapshot`, `blockers`, nullable `validatedAtUtc`, live `canPrepare` and nullable `pendingCommand`. The latter is exposed only to the original preparing subject who still has prepare permission. No subject, internal claim, decision ID or audit history is returned.

POS stores branch/date, Restaurant ownership, current configured timezone/currency, half-open UTC window, reviewed amounts/tenders, operational counts, owner evidence fingerprints and observation times, historical recorded-check identity/time, capture time and blockers. Existing [business-date and amount bases](End-Of-Day-Draft.md) apply; historical dates use current branch calendar configuration. Capture rejects inconsistent scope/calendar, currencies, counts, amounts and future observations. A dependency rejecting an incomplete/current date yields a blocked `source_unavailable` preparation rather than a usable day snapshot. Invalid command identifiers, default/max dates, negative versions and unknown reasons return 400 before persistence.

Blockers include unresolved orders/payments/refunds, open shifts/cash sessions, pending cash reviews, missing receipts/publications, mismatched projections, missing/gapped historical financial checks and unavailable owner fingerprints. Unknown issue codes block. `recorded_check_is_historical` is informational, never a completeness certificate. Nonzero `cash_variance` remains in the snapshot and is informational only when there are no pending reviews; POS already requires approval of every nonzero current drawer financial version. Summed variances can cancel, so pending review count is checked independently.

Every GET or completed replay of a Ready record obtains fresh evidence. Changed fingerprints, scope/calendar, totals/tenders, counts or blockers atomically invalidate readiness, advance the version and append an audit entry. Invalidation retains the original snapshot and adds `source_evidence_changed`; a source failure adds `source_unavailable`. Only an explicit new prepare replaces the reviewed snapshot. Blocked/Preparing reads return retained state without source polling; they never claim readiness. A failed refresh completes Blocked with no new snapshot; prior evidence remains in immutable audit. Concurrent replacement during validation returns 409 instead of serving an unvalidated Ready version. Caller/deadline cancellation returns no readiness; an interrupted command can remain Preparing.

Operation IDs are unique per organization. The fingerprint binds exact scope, date, expected version, reason and authenticated subject. Reusing an ID with changed payload/actor conflicts. Exact completed replay does not replace the reviewed snapshot or repeat preparation audit; its returned current Ready record still reads fresh evidence and can append invalidation audit. Row locks serialize one branch/day, expected versions fence competing managers, and network reads happen outside transactions. A 30-second lease permits the original actor to resume the exact pending command after expiry. A new operation using the current version can replace expired work; the old operation is abandoned and its claim cannot complete. No automatic retry, background expiry mutation or background source invalidation is supplied. Reload saved state before a new attempt, or explicitly retry the same operation after its lease expires.

## Evidence fingerprints and failures

Order, Payment and POS add nullable `evidenceVersion` to their version-one day summaries. Each owner selects its own relevant identities/statuses/versions/immutable evidence inside the same repeatable-read transaction as its totals, orders canonical JSON rows by identity, and computes a length-delimited SHA-256 including owner scope and window. Shared infrastructure only hashes bounded rows; it contains no selection or readiness policy. Observation timestamps do not participate. Identity/version changes invalidate even when totals remain identical. Fingerprints are observation identities, not monotonic revision numbers, delivery watermarks, verified receipt hashes or a cross-service snapshot.

At more than 10,000 selected rows or 16 MiB of selected UTF-8 evidence an owner returns a null fingerprint. Older adapters also return null. The draft can still load, but preparation blocks with `source_evidence_unavailable`; no partial fingerprint is accepted. This bounds hash input, not all aggregate query work. POS bounds the Reporting draft body to 128 KiB. Financial bodies, source evidence rows, tokens, subjects, reasons and arbitrary headers are never logged.

All routes are no-store, including authentication/error responses. 401/403 denote authentication/live access failures, 400 invalid commands, 409 active lease/stale version/operation conflicts, and sanitized 503 hierarchy/Authorization/database/overall timeout failures. A source read/transport timeout or invalid draft during preparation persists a successful command result with `blocked/source_unavailable`; during Ready validation it invalidates saved readiness. Client cancellation or the 25-second overall deadline may leave pending work; a later authorized load/resume recovers it. The entire Reporting evidence read, including headers and streamed body, has a linked 15-second deadline inside the 25-second POS Application deadline. BFF has a 30-second deadline and the browser 40 seconds.

The portal adds Load/Prepare/Refresh/Resume/Replace controls below the existing read-only draft filters. It clears previous results during requests, filters, tenant changes and failures, discards late responses, validates scope/readiness before display and preserves uncertain command identity for explicit retry. After a browser restart, load the saved record to recover the original actor's pending command. A different authorized manager can explicitly replace interrupted work using the loaded current version; the server rejects replacement before lease expiry. Accountants see no prepare controls. No browser storage contains financial snapshots or bearer tokens.

Use `{service_name="nexaconnect-pos"} |= "Day-close"` and `{service_name="nexaconnect-customer-bff"} |= "Day-close"`; narrow by validated `CorrelationId`. New HTTP clients adopt shared structured JSON/OTLP request telemetry and outbound correlation propagation. Safe events record completion status, authorization/conflict boundaries and failure category, never financial payloads.
