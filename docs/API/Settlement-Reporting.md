# Settlement reporting

The bounded [settlement CSV export](Settlement-Export.md) adds `GET .../day-settlements/export.csv` through Reporting and the Customer BFF. Each download runs a fresh authorized ledger comparison; original amounts, correction proof and delivery gaps remain distinct. Existing permissions and schemas apply; see [ADR-036](../Architecture/Decisions/ADR-036-bounded-settlement-export.md).

Settlement original-event replay is now provided by [ADR-035](../Architecture/Decisions/ADR-035-audited-settlement-replay.md) and [the administrative runbook](../Deployment/Settlement-Replay.md). POS 23 adds two immutable audit tables; Reporting stays 22 and compatibility is 0.38.0 (201 tables, POS 52 / Reporting 19). Customer routes/permissions remain read-only; unknown original publication fields fail closed.

`GET /api/pos/v1/customer/settlement-manifest?organizationId={id}&branchId={id}&fromDate=yyyy-MM-dd&toDate=yyyy-MM-dd` returns retained original settlement publications. Dates select the branch business date, inclusive from/exclusive to; they do not select UTC decision time. Maximum range31 dates,31 receipts and1000 correction items; response is at most2MiB. Upper date is bounded to UTC today plus one day to accommodate branch calendars. This grants no current-day settlement authority.

POS resolves the live Restaurant hierarchy and requires existing `pos.day-close.read` with the customer's bearer. The response includes owning organization/Restaurant/branch, exact date range, observation time and `events` containing exactly one of `v1` or `v2` per committed receipt. Durable commit decision, receipt and original outbox identity, correlation, aggregate type/ID, timestamp, version and payload must agree. An absent committed receipt or missing, corrupt or unsupported original evidence returns503; bounded range overflow returns400. Source selection uses one repeatable-read transaction. The inventory includes durable commit decisions with receipts, including acknowledgment recovery still in progress; it excludes aborted/uncommitted attempts.

`GET /api/reporting/v1/customer/organizations/{organizationId}/reports/day-settlements?branchId={id}&fromDate=yyyy-MM-dd&toDate=yyyy-MM-dd` requires live `reporting.sales.read`, authenticated subject and matching organization/application context. Reporting forwards the customer bearer through its correlated POS adapter and never substitutes workload authority. Source failure/denial prevents a projection-only success response.

`GET /bff/customer/reports/day-settlements` accepts the same branch/date filters, takes organization/application/subject from the protected tenant cookie, renews the server-held access token and revalidates Directory membership. No financial POST or CSRF token is needed for this read-only capability. Cookies/tokens and private Authorization decisions are absent from all results.

The report contains scope/dates, `sourceObservedAtUtc`, `comparedAtUtc`, normalized manifest hash, `status=matched|gaps`, independent expected/matched/missing/conflicting/unexpected counts and at most 62 rows. Selected POS evidence contains at most 1000 correction items; combined expected and unexpected report rows contain at most 2000. Each row includes event/settlement/date/approval/seal identity, source seals, exact THB decimal strings for gross sales/refunds/net/cash variance, original contract version, delivery status and correction proof. Expected missing/conflicting rows display authorized original POS values; they do not imply those values reached Reporting. Unexpected rows contain only this authorized scope. Financial conflicts never expose foreign values. The portal rejects malformed scopes, arithmetic, counts and proof, and clears results on access failure or changed filters/context.

V1 rows have `correctionEvidence=historical_unavailable`, null correction/window/decision fields and original totals. V2 rows have `correctionEvidence=verified`, decision/window and exact correction manifest/epoch/revision/hash/counts/items. Adjustments are exact decimal strings; expected=matched, other correction counts zero, items/negative adjustment agree, and provenance matches the original POS seal. These counts describe the already reviewed correction proof retained in that receipt, separately from this report's settlement-delivery counts. No browser amount or correction command is accepted.

Correction adjustment is displayed as a separate explanation of the retained evidence. The POS snapshot's `cashVariance` already includes its selected corrections; readers must not add the adjustment again to variance or net sales. The report preserves those original totals and does not calculate a new settlement balance.

New `BranchDaySettledV2` nests unchanged V1 financial fields and carries V2 proof under routing key `pos.branch-day-settled.v2`, contract version2 and aggregate type `branch-day-settlement`. Event/correlation/time agree across envelope and nested financial fields. The receipt retains its original event ID. Each new commit emits one V2 event. Legacy V1 history remains unchanged and the consumer accepts both versions. A hash receipt binds the complete normalized financial/proof model; equal totals cannot conceal changed identities, corrections or sources.

Responses are bounded/no-store with sanitized400/401/403/503. POS/source clients use15-second deadlines, Reporting comparison25 seconds and BFF30 seconds. Observations use separate snapshots and may change after later commits or delivery; `matched` means the selected original set matches, not a global watermark or completed source acknowledgments. See [ADR-034](../Architecture/Decisions/ADR-034-settlement-reporting.md) and [operations](../Deployment/Settlement-Reporting.md).
