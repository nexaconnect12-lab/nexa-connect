# Correction-aware day-close evidence

`CashCorrectionEvidenceFingerprint` defines version-one integration encoding: EventId-sorted original identity/financial fields, normalized UTC instants and decimal scale, serialized and SHA-256 hashed. Reporting produces this value and POS independently recomputes it from retained original events before accepting delivery proof. Shared code contains encoding only; financial validation and admission remain service-owned.

The existing cutoff/seal routes gain protocol-3 POS correction proof. Order/Payment manifests stay at protocol 2; fresh POS manifests contain `evidenceProtocolVersion:3` and `cashCorrections` (ADR-032 `CashCorrectionManifest`). Its exact window, owning scope, original events, count, negative THB adjustment, source summary and epoch/revision are captured together. Inventory is capped at 1000; an empty inventory is explicitly retained, not inferred from absent fields. Original event/ledger inconsistency rejects capture; no replacement event is invented.

`POST /api/reporting/v1/customer/day-cutoff-reconciliation` now requires `{window,orderManifestId,paymentManifestId,posManifestId}`. Seal reconciliation requires `{window,orderSealId,paymentSealId,posSealId}`. Missing POS references return 400. Source/customer authorization is revalidated through the existing financial read APIs; Reporting requires live `reporting.sales.read` and resolves organization/Restaurant/branch. POS source cut reads require its existing `pos.cash-review.read`; POS coordination additionally requires `pos.day-close.read` and command-specific grants. Bearer/correlation propagate through existing bounded HTTP clients. No workload bypass or new grant is introduced.

Cutoff responses add `posManifestId`, `posRevision`, `cashCorrections` and protocol 3. Seal responses add `posSealId`, `cashCorrections` and protocol 3. The correction proof contains `{posManifestId,posRevision,manifestHash,counts,adjustment}`; adjustment is an exact decimal string. Counts independently describe expected/matched/missing/conflicting/unexpected financial identities and receipt hashes. Missing/extra/changed identity or hash blocks delivery regardless of totals. Foreign conflicting projection values are not disclosed. POS source selection is read again after comparisons; changed retained references/provenance fail closed, and current/suffix failure prevents delivery completeness.

Fresh POS cutoff/seal/approval/settlement snapshots contain `corrections`: POS manifest/epoch/revision, opaque manifest hash, exact `adjustmentText`, independent counts, and bounded items identifying original event/correction/settlement/work/Order/tender/drawer, posting date/time and exact adjustment text. Internal numeric values remain server-owned; the portal displays and validates strings without rounding. No correction posting amount, arbitrary date or actor is accepted in these commands. Existing actor/claim/Authorization audit privacy boundaries remain unchanged.

Domain blockers include `correction_evidence_unavailable`, `correction_delivery_unproven`, `correction_delivery_missing`, `correction_delivery_conflicting`, `correction_delivery_unexpected`, alongside existing revision/financial/journal blockers. Blocked evidence remains saved for review. Exact original-event delivery or administrative replay can close a projection gap; managers then explicitly refresh, review and seal. Readiness is freshly validated, not permanently inferred from a previous check. New source generations or correction identities are not interchangeable merely because amounts match.

Correction evidence follows the reviewed seal into approval and the immutable settlement receipt. Newly prepared/finalized admission requires complete, internally consistent proof. Later relevant or unknown changes invalidate affected readiness through existing journals; independent later-day changes preserve old sealed evidence. Original sales/tenders and old drawer/settlement receipts stay unchanged.

Historical protocol-two POS manifests remain readable and exact source-operation replay returns them with `current=false`; refresh using a new operation. Existing finalized receipts and historical approval decisions can omit correction proof. They are read as history, not accepted as fresh protocol-3 candidates. Ordinary non-cutoff preparation remains a separate observational draft and grants no settlement authority.

All source/Reporting/BFF responses retain bounded no-store and sanitized error handling. Correlation, live denial/failure events and JSON/OTLP remain in the shared foundation. Source cut windows are closed positive UTC intervals up to 27 hours; coordinator windows derive from a completed branch-local date. A current-day partial UTC cut cannot authorize production whole-day settlement.
