# Sale and payment financial reporting

Order publishes `order.sale-completed.v1` for every application Paid path: foreground provider checkout, recovery, capture reconciliation, and manual cash or verified PromptPay settlement. It reads the retained version-1 receipt in the same transaction as Paid, records one immutable `order_sale_publications` payload, and enqueues it atomically. The event UUID is deterministically derived from the Order UUID. Concurrent completion uses the persisted winning receipt, never a new timestamp or current Catalog price. The publication survives outbox cleanup.

The event carries tenant/restaurant/branch scope, Order and payment identity, payment origin and method, channel/service type, original Order creation time, receipt Paid time/number, currency, subtotal, service charge, tax and total. Discount is zero in the current accepted pricing model. Provider payment identity is the intent UUID; manual identity is the settlement UUID. There are no customer details, bank references, line names, tokens or credentials. Existing completion and manual-tender events retain their contracts and consumers.

Reporting translates the contract into its own validated financial fact. One transaction inserts a normalized SHA-256 event receipt, `sales_facts`, `payment_facts`, and the `order-sale-financial` / `order.sale-completed.v1` checkpoint before acknowledgement. Financial hashing normalizes timestamps to UTC and equal decimal values to four-place scale, so equivalent offset/amount formatting replays as a no-op. A changed financial fact for the same event, or an already used Order/payment identity, fails closed and dead-letters without partial writes. Transient database/broker failures retry. Sales do not depend on refund delivery order; refund facts remain separately owned and preserved.

`payment_facts.payment_intent_id` retains its existing column name and stores the payment identity, distinguished by new `payment_origin` (`payment_intent`, `manual_settlement`, or pre-existing `legacy_unknown`). New rows use `payment_status=paid`, original receipt time, and `refunded_amount=0`. The provider code is left null because Order's receipt does not establish it. No fabricated provider reference is introduced.

Existing HTTP routes, live permissions and tenant/branch filters remain unchanged. Sales gross amounts use `ordered_at_utc`; payment amounts use `paid_at_utc`; refunds use `refunded_at_utc`, all in half-open UTC ranges. `netSales` subtracts refund-period amounts from sales-period gross amounts. `netPaid` retains its existing payment-fact formula; the new completion pipeline does not update its legacy refunded amount, so this is received-payment evidence, not refund-adjusted settlement accounting. Refunds do not reduce original sale totals. Mixed currencies fail closed. Checkpoint freshness is processing activity, not a completeness watermark.

Apply **Order 11 and Reporting 19**, minimum application **0.22.0**, before deploying the changed binaries. Order 11 adds immutable publication and attributed replay audit tables. Reporting 19 adds dedupe receipts and payment origin; existing facts remain `legacy_unknown` and are never silently overwritten. Both downgrades refuse after recorded publication/projection evidence; roll forward. The defaults in Reporting appsettings leave consumption disabled.

Configure `OrderSaleConsumer__Enabled=true`, secret-managed TLS `OrderSaleConsumer__ConnectionString`, Order-matching `OrderSaleConsumer__Exchange` (default `nexaconnect.events`), durable `OrderSaleConsumer__Queue` (default `nexaconnect.reporting.order-sales.v1`), and bounded `OrderSaleConsumer__PrefetchCount` (default 16, clamped 1–100). Establish the durable queue/binding and verify `Order sale financial consumer ready` before starting the new Order binary/outbox dispatcher. Events published before a binding exists need controlled replay.

Use service `nexaconnect-reporting`, Loki `{service_name="nexaconnect-reporting"} |= "Order sale financial"`, and metric `reporting.order_sale.outcomes` (`applied`, `replayed`, `rejected`, `retry`, `connection_retry`). The worker uses Reporting structured logging and OTLP; validated correlation IDs scope processing. Monitor queue/dead-letter depth and Order outbox age. Bodies, amounts, personal data and credentials never enter logs. Rejecting a conflict requires inspection of authoritative evidence; do not overwrite report rows as repair.

The [recovery tool](../../src/Tools/NexaConnect.SaleReportingRecovery/README.md) previews exact tenant/branch/receipt-Paid windows, backfills retained receipts, requeues original publications with append-only operator attribution, and compares expected evidence with Reporting. It uses service-owned persistence boundaries and never writes Reporting. Reconciliation can lag after asynchronous replay; rerun inspection after consumption catches up.

Verify `SaleFinancialReportingTests`, `SaleFinancialProjectionPostgresTests`, `PaidOrderReceiptPostgresTests`, `OrderPricingPostgresTests`, and migration catalog tests. Live integration requires disposable PostgreSQL, `NEXACONNECT_REPORTING_INTEGRATION_DB`, Testing/Development environment, and for RabbitMQ `NEXACONNECT_RABBITMQ_ACCEPTANCE=1` with `NEXACONNECT_RABBITMQ_INTEGRATION_URI`. Order receipt/pricing acceptance additionally requires `NEXACONNECT_PRICING_ACCEPTANCE=1`, `DOTNET_ENVIRONMENT=Testing`, and `NEXACONNECT_ORDER_INTEGRATION_DB`. Tests cover concurrency, exact/conflicting replay, transaction failures, tenant isolation, retained receipt time, refund-before-sale, consumer restart/out-of-order delivery and dead-letter rejection.

Clean-database runner verification uses `OrderMigrationRunnerAcceptanceTests` and `SaleReportingMigrationAcceptanceTests`. Set `NEXACONNECT_ORDER_CLEAN_INSTALL_ACCEPTANCE=1`, `NEXACONNECT_POSTGRES_ADMIN_INTEGRATION_DB` to a disposable administrator connection with database-create capability, and a Development/Test/Testing environment. The cases create and remove generated databases, exercise Order 11 / Reporting 19 upgrade, empty-history downgrade/re-upgrade, representative writes, and forward-only guards after evidence. These are separate from fixture-schema projection tests and remain environment-specific release checks.

This slice supplies completion projections and scoped evidence reconciliation. Historical Paid rows without a receipt are explicit gaps. Refund historical replay, all-source completeness certification, item-sales projection, split tenders, discounts, manual refunds, fiscal credit notes and settlement accounting remain follow-up work. A passing scoped reconciliation is not a certification of every financial source.

Local verification completed the full solution suite (773 passed, 104 skipped) and nine live database/broker cases with zero skips, including actual Order 11 and Reporting 19 migration runners.
