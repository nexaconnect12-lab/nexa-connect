# Cash correction Reporting

Reporting consumes the original `pos.late-cash-correction-posted.v1` / `PosLateCashCorrectionPostedV1` contract through its opt-in `CashCorrectionConsumer`. An anti-corruption translation validates nonempty identities, positive reviewed version, THB, a negative four-decimal adjustment and a posting instant inside the retained posting interval. Reporting owns separate facts and SHA-256 event receipts; receipt, fact and checkpoint commit atomically before acknowledgement. Exact repeats acknowledge without another fact; conflicting event or correction/work/tender/Order identities dead-letter. Transient failures requeue. No sale, payment, refund, drawer or original settlement projection is updated.

`GET /api/reporting/v1/customer/organizations/{organizationId}/reports/cash-corrections?branchId={uuid}&fromUtc={iso}&toUtc={iso}` performs a **fresh live comparison**, unlike the older recorded sale/refund completeness route. Organization/product tenant headers, current membership and live branch `reporting.sales.read` are required. Reporting forwards the customer's bearer to POS; POS independently resolves organization/Restaurant/branch and requires `pos.day-close.read` plus `pos.cash-review.read`. No workload token can substitute for these customer permissions.

POS exposes `GET /api/pos/v1/customer/cash-correction-manifest?organizationId={uuid}&branchId={uuid}&fromUtc={iso}&toUtc={iso}`. Its repeatable-read inventory compares each immutable ledger receipt against the retained original outbox event, exact references/amount/date, posting bounds, correlation and database timestamp precision. Missing or conflicting retained publication evidence fails closed. Original event identities are preserved; no replacement publication is invented. Actor, Authorization decisions, provider data, request bodies and original tender payloads are excluded.

Both windows are explicit, half-open UTC, positive, already closed and no longer than 31 days. POS rejects more than 1000 corrections instead of truncating. Reporting also bounds its inventory and total returned rows (2000); narrow an oversized window. Source and Reporting snapshots are separate. The source observation timestamp is POS host UTC at completion of the inventory read; it is not a database clock, transaction start or delivery watermark. Results are observations, not settlement certification or delivery watermarks.

The no-store response identifies organization/branch/window, source and comparison times, a sorted source-fact manifest hash, `status` (`matched` or `gaps`), `expected`, `matched`, `missing`, `conflicting`, `unexpected`, and separate exact-string `sourceAdjustment` / `projectedAdjustment`. Safe detail rows identify event/correction/original settlement/work/Order/tender/drawer, posting day/time, THB adjustment and comparison status. Expected events are checked by identity even when an existing projection has wrong scope/time. Other-tenant conflicting values never enter returned rows or totals. Unexpected rows are restricted to the selected organization/branch/posting window. `matched` requires all identities, financial values and receipt hashes to agree; equal totals alone are insufficient. An empty valid inventory matches with zero counts.

Invalid input or oversized source/projection inventory is 400; live denial is 403; source/database/transport evidence failure is sanitized 503. Early authentication and all failures remain no-store. Source calls have 15-second timeouts, Reporting use cases 25 seconds and BFF forwarding 30 seconds; adapters buffer at most 2 MiB.

`GET /bff/customer/reports/cash-corrections` accepts branch/window only. The BFF derives organization from the protected subject-bound tenant cookie, checks current product membership and uses server-held refreshed tokens. Browser organization/actor overrides are ignored. The End-of-day page exposes independent UTC-window comparison controls, exact adjustments, counts and detail rows; unavailable, malformed or changed-scope responses clear prior results, and aborted old requests cannot restore them. Browser reads perform no posting or replay.
