# Settlement rollout and forward recovery

The versions below identify the settlement capability boundary. Current review-enabled binaries additionally require [late-work review rollout](Late-Work-Reviews.md): Order 19 / Payment 18 / POS 19 / Authorization 14 at compatibility 0.33.0, with Reporting 20 unchanged.

Deploy **Order 18 / Payment 17 / POS 18 / Authorization 13**, minimum application compatibility **0.32.0**, matching Customer BFF/Portal and unchanged Reporting 20. Stop old financial writers during coordinated migration/deployment. POS 17 supplies its source barrier; POS 18 supplies the coordinator. Mixed versions cannot safely enforce permanent protection. The migration launcher defaults to 0.35.0.

POS requires existing `WorkloadIdentity:Authority`, `ClientId=nexaconnect-pos-service` and protected `ClientSecret`, plus `Services:Order`, `Services:Payment` and `Services:POS` (the self-source HTTP address), existing Reporting/Restaurant/Authorization dependencies and API-audience issuance. The service-account token must carry the exact preferred username specified in ADR-029. No additional client or secret is introduced. Set `SettlementRecovery:Enabled=true` (`SettlementRecovery__Enabled=true` in environment configuration) on deployed POS hosts before allowing operators to finalize. Routes are registered regardless of this setting; it controls unattended recovery only. The worker is opt-in; without it, only explicit permitted exact retries drive recovery. Ordinary POS outbox configuration controls publication; the settlement decision always retains the original event even when publishing is disabled.

Each source adds four tables: `source_day_barriers`, immutable `source_day_barrier_audit`, `source_late_work` and `source_late_work_links`. Keys bind organization/settlement, globally scoped finalize and preparation operations, exact window/fingerprint and local fence FK. Terminal decisions, audit, payloads and links reject rewriting/deletion/truncation. Financial journal guards check durable barriers before temporary leases and raise SQLSTATE `PDS01`; the whole owning financial transaction rolls back. Barrier generation updates serialize old repeatable-read writers without inventing financial journal entries.

The realm template includes `pos-service-account-username`, an access-token-only user-property mapper for the existing POS workload client. Apply it explicitly to persisted realms; a Keycloak restart skips existing-realm import. Keep the existing API audience mapper and disabled browser/password flows, then obtain a fresh POS workload token. The optional `profile` scope is not requested and must not be relied on to supply this claim. See [Keycloak mapper lifecycle](../../docker/keycloak/README.md). Validate the template with `scripts/test-keycloak-realm.ps1` and privately verify target-environment token claims; never retain tokens in acceptance evidence.

Source HTTP write rejection returns correlated, sanitized, no-store 409 with `code=financial_day_barrier` for permanent barriers or `code=financial_day_fenced` for temporary leases. Cancelling a pinned customer source fence also returns 409 `financial_day_barrier`. These failures roll back the owning financial transaction; they do not remove protection.

POS adds five tables: `branch_day_settlements`, immutable `branch_day_settlement_operations`, `branch_day_settlement_decisions`, `branch_day_settlement_receipts` and `branch_day_settlement_audit`. A partial unique day index permits one non-aborted attempt; aborted history remains retained. Scope and local preparation/decision FKs enforce ownership. Commit decision, receipt, audit and outbox row share one local transaction; acknowledgement status updates never rewrite the receipt. Existing temporary preparation is pinned while settlement remains active.

Each source migration includes `source_day_barriers_window` on `(restaurant_id,branch_id,from_utc,to_utc)` restricted to armed/committed barriers for financial admission, and `source_late_work_by_barrier` on link `(organization_id,barrier_id)` for retained counts. POS includes unique `branch_day_settlement_operation_lookup` on organization plus JSON command operation ID for exact replay, and `branch_day_settlement_recovery_queue` on `(last_attempt_at_utc,id)` restricted to non-finalized/non-aborted intents for bounded recovery. These indexes are part of the new owning migrations; they add no cross-service dependency or history mutation.

Runtime grants, in each owning schema, must permit SELECT/INSERT on source barrier/audit/custody/link tables and UPDATE(`phase`,`decision_id`,`changed_at_utc`) on `source_day_barriers`. Keep existing fence cancellation/audit and financial revision generation privileges. POS additionally needs SELECT/INSERT on all five coordinator tables, UPDATE(`state`,`last_attempt_at_utc`) on `branch_day_settlements`, and existing outbox INSERT. These are owning-service permissions only: no cross-database grants, schema/table ownership, trigger-disable, DELETE or TRUNCATE. Do not expose late payloads to report roles. Migrations remain deployment-only DDL.

Recovery behavior:

- Lost response, crash or dependency/authentication outage: retain the exact command; load progress. The bounded worker processes up to ten intents, attempts each with a 25-second deadline and repeats after five seconds. Failed attempts remain durable; dependency failures do not select abort or unlock.
- A permanent source arming conflict selects a retained abort decision. Recovery sends that same decision to all three sources, including unarmed tombstones, and cancels original leases. Source expiry before arming may force this path; expiry after arming never releases protection.
- Once commit exists, missing source acknowledgements are delivery work. Restore the failed dependency/credential and let recovery finish. Manager revocation prevents new customer commands but does not revoke the already committed delegated intent.
- SQLSTATE `PDS01` blocks ordinary financial commands with rollback. Recover through their owning workflow; do not bypass the guard. Supported delayed deliveries first retain bounded normalized custody. Armed-only messages stay in their original channel and retry, so abort can resume normal application. Committed custody is acknowledged only after its transaction commits and awaits a future correction workflow.
- POS manual-tender and Order reconciliation retry held broker messages with a one-second delay; Payment `barrier_held` remains pending without exhaustion and `late_captured` completes the canonical webhook inbox. No provider financial command is initiated by custody. Duplicate identity with changed content conflicts.
- Existing custody is checked before financial writes on replay. Committed custody remains acknowledged without applying the original financial mutation; armed custody remains held until a retained abort releases it. Order also checks custody identity/content on already-completed inbox duplicates. Changed retained broker payloads are rejected to dead-letter rather than repeatedly retried; webhook identity conflicts follow the existing bounded retry/exhaustion path.
- Fresh GET attempts source counts; failure returns saved progress with `sourceProofCurrent=false`. Original receipts and status are durable independently of observation freshness.

No new worker may remove barriers or overwrite decisions. Restore source/POS databases consistently with retained evidence; an epoch reset or missing history requires investigation and forward recovery. New migrations reject downgrade once retained settlement/custody exists. Empty rollback runs in reverse order: POS 18 before POS 17/16; source barrier migrations before original fence removal. Disable new routes/workers before Authorization downgrade. Production acceptance and operational restore drills remain required before release.

Telemetry uses existing `nexaconnect-pos`, `nexaconnect-order`, `nexaconnect-payment`, `nexaconnect-customer-bff` JSON/OTLP resources. POS registers ActivitySource/Meter `NexaConnect.POS.SettlementRecovery`, span `settlement.recover` and counter `settlement.recovery.attempts` with bounded outcome labels. Search logs for `Settlement recovery`, `Settlement barrier`, `Payment reconciliation deferred by settlement` and validated `CorrelationId`; inspect retry counts and committing/aborting backlog. Logs exclude tokens, cookies, bodies, payment data, arbitrary headers, provider failure text and subjects.

Each recovery attempt supplies explicit `CorrelationId` and `TraceId` logging scopes so JSON diagnostics can be joined to source HTTP requests and OTLP traces after restart.

Order payment reconciliation uses ActivitySource/Meter `nexaconnect-order`, consumer span `payment-reconciliation.process` and counter `order.payment_reconciliation.outcomes`. Bounded outcome labels are `applied`, `replayed`, `held`, `late_captured`, `retry` and `dead_lettered`. Its JSON logs carry correlation/trace scopes; narrow `Payment reconciliation` diagnostics by `CorrelationId` and inspect the outcome counter alongside settlement backlog. No payload, provider failure text or subject is logged.
