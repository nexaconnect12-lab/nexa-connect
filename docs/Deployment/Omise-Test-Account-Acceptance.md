# Omise test-account adapter and acceptance

After the successful direct test-account gate, the [hosted Omise interruption harness](Omise-Hosted-Recovery-Acceptance.md) is available with four fresh independent tokens. Its credentialed four-scenario execution passed on 2026-09-17; it covers response loss and hosted outbox restart, and historically excludes the pre-authorization boundary. The new `-IncludeCardTokenHandoff` opt-in adds that fifth boundary, with credentialed five-scenario execution passed on 2026-09-18; see the [test-only handoff guide](Omise-POS-Card-Token-Handoff.md).

Payment now supports `PaymentProvider:Adapter=Omise` for THB card transactions in Development or Testing. This slice is test-account-only: startup rejects live keys and other environments, uses the fixed `https://api.omise.co/` endpoint, disables HTTP redirects and retains platform certificate validation. GenericHttp and the fail-closed Disabled default are unchanged. No migration is needed; existing Payment authorization/capture/void leases, audit, outbox and recovery workers remain authoritative.

## Configuration and input

Configure `PaymentProvider__Adapter=Omise` and inject `PaymentProvider__OmiseSecretKey` from your secret manager or process environment. The key must be `skey_test_...`. Do not put it in appsettings, source control, command arguments or chat. `PaymentProvider__RequestTimeout` remains bounded at startup. For Omise, `PaymentProvider__LeaseDuration` must cover four request-timeout periods plus ten seconds (two bounded header/body exchanges); the existing defaults of 15 seconds and two minutes satisfy this guard. Authorization, capture and void recovery register with PostgreSQL persistence; existing capture/void pause switches still apply. Omise does not use GenericHttp's BaseUrl/path/ApiKey or simulator certificate pin.

The existing internal Order-workload authorization route accepts an optional JSON body:

```http
POST /api/payment/v1/intents/{intent-id}/authorize
Content-Type: application/json
X-Nexa-Organization-Id: <organization-id>

{"cardToken":"tokn_test_<fresh-token>"}
```

An authenticated exact `nexaconnect-order-service` workload is still required. Body size is capped at 1024 bytes. For a pending Omise intent, a missing/invalid test token returns 400 before acquiring a lease or calling Omise. Missing/cross-organization intents return 404 and other workloads receive 403. Replays after authorization starts observe the existing state without another provider command or a new token. GenericHttp callers can continue sending an empty body.

Card tokens remain ephemeral: they are forwarded only for the initial charge creation, never stored on an intent, serialized in its response, copied into events/audit or logged. PAN/CVV must go directly from approved client-side tokenization to Omise; NexaConnect does not collect them. Omise tokens are single-use, even when a charge fails. See [Omise card collection](https://docs.omise.co/collecting-card-information/malaysia) and [test cards](https://docs.omise.co/api-testing).

The current Order/POS workflow has opt-in Development-only test-token handoff. Configure the guarded `card_omise_test` path using the [handoff guide](Omise-POS-Card-Token-Handoff.md); manual tender remains the default. The direct and historical four-scenario hosted passes do not certify live POS/OIDC UI acceptance or the new fifth interruption scenario. Do not supply a global reusable token through configuration.

## Recovery behavior

The adapter uses Basic authentication with the secret as username and an empty password, pins API version `2019-05-29`, converts exact two-decimal THB to satang, and posts `/charges` with `capture=false`. It adds Payment intent, organization and Order UUID metadata plus a versioned full-capture mode and HMAC proof of that request context. Charge response currency comparison accepts uppercase or lowercase THB; other currencies remain rejected. Authorization succeeds only for a matching test charge with authorized, unpaid, unreversed, capturable state and deferred capture. A confirmed failed/expired/reversed charge is definitive failure; pending/3DS, malformed, already-paid or ownership/amount mismatches remain unknown. 3DS redirection is not implemented.

Capture uses `/charges/{id}/capture`; the local pre-capture void maps to `/charges/{id}/reverse`, not refunds. Both fetch the current bound charge before a command, verify metadata/amount/currency/test mode, and return an established terminal result without another POST. Capture completes only with zero refunds and exact full capture evidence. An explicit captured_amount must equal the intent amount. When that field is absent, the adapter requires returned authorization_type=final_auth plus successful, authorized, paid, unreversed, deferred-capture, non-capturable and non-reversible state. When authorization type is absent too, signed full-capture creation context can establish the requested mode; otherwise absent type and conflicting/partial evidence remain unknown. The default type is never inferred from an absent response field. New authorizations explicitly request final_auth. See [Omise full manual capture](https://docs.omise.co/capture/thailand). A paid charge cannot be reversed. Provider responses changing the bound charge ID cannot confirm either command.

There is no automatic POST retry or assumed Omise idempotency-header contract. Durable Payment leases fence command starts. Uncertain results use status-only recovery; command replay after local completion returns the original result. When an authorization response was lost before its charge ID was committed, recovery queries `/search?scope=charge&query=<intent-uuid>&per_page=100&page=1`, requires exactly one exact metadata-bound candidate on one page, then fetches that charge fresh. Missing, ambiguous, mismatched, paginated or eventually inconsistent results remain unknown and eventually require review under existing bounded policy. Recovery never creates a replacement charge or retries a consumed token. All HTTP errors, timeout/transport failures and invalid success payloads remain uncertain until status confirms the financial outcome. Response parsing is capped at 64 KiB and body reads have a deadline.

Official contracts: [authentication](https://docs.omise.co/api-authentication), [charges/capture/reversal](https://docs.omise.co/charges-api), [search](https://docs.omise.co/search-api/singapore), and [metadata search](https://docs.omise.co/search-query-and-filters/malaysia).

## Run the real sandbox gate

1. Open your Omise test dashboard and retrieve the test secret key under API → Keys.
2. Use the [local HTTPS token helper](../../src/Tools/NexaConnect.OmiseTokenHelper/README.md) with your own test public key. The documentation simulator blocked Vault requests under its CSP during this setup; use the local helper to avoid that page-dependent limitation. Generate and copy one token for capture, then a second for void. Alternatively generate two distinct fresh test card tokens using Omise's approved tokenization with your test public key and a documented non-3DS success test card. Send test card details directly to Omise, never through NexaConnect. The public key is used by that client; Payment only needs the secret key and transient token.

   Start the helper from the repository root in a separate terminal:

   ```powershell
   dotnet dev-certs https --trust
   dotnet run --project src/Tools/NexaConnect.OmiseTokenHelper --no-launch-profile -- --environment Development
   ```

   Open `https://localhost:54443` after startup. Enter only `pkey_test_...`, click **Generate fresh token**, and then **Copy token**. The helper uses a fixed success test card; no card details or tokens go to its server. Keep the page open to generate the second token when the void prompt appears below. Trust only the normal .NET development certificate through the command above; do not bypass a browser certificate warning. Stop the helper with Ctrl+C, close the page and clear the clipboard when finished. Credentialed token generation remains unverified until run with your account.

3. In PowerShell 7, inject the three values using masked prompts in the same terminal that will launch acceptance:

```powershell
$env:NEXACONNECT_OMISE_TEST_SECRET_KEY = [Net.NetworkCredential]::new('', (Read-Host 'Omise test secret key' -AsSecureString)).Password
$env:NEXACONNECT_OMISE_CAPTURE_TEST_TOKEN = [Net.NetworkCredential]::new('', (Read-Host 'Fresh capture test token' -AsSecureString)).Password
$env:NEXACONNECT_OMISE_VOID_TEST_TOKEN = [Net.NetworkCredential]::new('', (Read-Host 'Fresh void test token' -AsSecureString)).Password
pwsh -NoProfile -File scripts/test-payment-omise-live-sandbox.ps1 -ConfirmSandboxTransactions
```

The default amount is 50.00 THB per authorization; `-Amount` permits exact two-decimal values up to 10000 THB, subject to Omise's account/provider limits. No real money is moved with test keys. .NET 10, restored dependencies and internet access are required; Docker is not required for this direct gate.

4. Expect exactly one unskipped passing integration test. It authorizes two charges, verifies authorization replay and reference-loss search, captures one, reverses the other, verifies replay/status identity, and rejects captured reversal. Successful identifier-free JSON is retained at `.runstate/payment-omise-live/<run-id>/summary.json`; successful TRX is removed. Failed runs retain restricted TRX diagnostics. Test charges remain in your Omise test account. On authorization failure, the gate reports only local state and a normalized failure category, without provider payloads or identifiers. A failed assertion does not establish whether a charge exists. Do not automatically rerun after ambiguity; inspect test-dashboard charges and use two new unused tokens for a new run.
5. Remove credentials from the shell when finished:

```powershell
Remove-Item Env:NEXACONNECT_OMISE_TEST_SECRET_KEY, Env:NEXACONNECT_OMISE_CAPTURE_TEST_TOKEN, Env:NEXACONNECT_OMISE_VOID_TEST_TOKEN -ErrorAction SilentlyContinue
```

## Observability

The adapter uses the shared `nexaconnect-payment` service and propagates validated correlation IDs. It emits safe `Omise {Operation} boundary returned {FailureCategory}; reconciliation required` events with method and bounded category only. Standard HttpClient loggers are removed for this client; request/response bodies, Basic credentials, tokens, card data and provider failure text are never logged. HTTP 400 error bodies are read with the same 64 KiB cap and timeout; only an error object with a recognized code can select a fixed local diagnostic category. Unknown codes, malformed or oversized error bodies retain provider_http_400. Recognized codes do not establish a definitive outcome or enable a retry. Query `{service_name="nexaconnect-payment"} |= "Omise"` in Loki, then follow `CorrelationId` through existing Payment/Order recovery logs. Shared JSON/optional OTLP and existing workers/outbox telemetry remain in place; no dedicated Omise metrics are added.

## HTTP 400 troubleshooting

Recognized Omise rejection codes are mapped to safe categories, with no provider message or payload retained. Examples: provider_token_used (used_token), provider_card_token_invalid (invalid_card_token), provider_charge_invalid (invalid_charge), provider_amount_invalid (invalid_amount), provider_feature_unsupported (feature_not_supported), provider_brand_unsupported (brand_not_supported), provider_multicurrency_failed (failed_multi_currency), provider_backend_error (backend_error), and provider_bad_request (bad_request). Expired/capture/reversal rejection codes are likewise diagnostic only. Only the fixed categories reach local failure diagnostics; arbitrary codes or messages cannot be logged or persisted. See [Omise errors](https://docs.omise.co/api-errors).

After inspecting test-account charges and resolving any existing authorization, a manually initiated new run requires two fresh, distinct tokens and keys from the same test account. Generate and inject each token via its masked prompt, then run the existing guarded command in that terminal. Report only the State/category assertion if it fails. ## Build troubleshooting

The sandbox runner builds the integration project with `--no-restore` before enabling the live gate, retains `build.log` in its run directory, and reports build failures separately from payment-test failures. A build-only failure occurs before provider requests and does not consume either token. The test phase uses `--no-build`; if a token becomes stale during troubleshooting, generate fresh tokens before the next test run. For build errors, inspect `build.log` and share the compiler/MSBuild error line rather than the wrapper exception.

## Responses omitting both capture amount and authorization type

New authorizations explicitly request final_auth and retain nexa_capture_mode=final_auth_v1 plus an HMAC-SHA256 proof in provider metadata. The proof binds canonical Payment intent/organization/Order UUIDs, exact integer satang, THB and a domain-separated versioned mode to the current test secret. It is not a token, stored key, logged value or ownership/settlement attestation. It binds request context rather than a unique provider charge ID; identical context copied to another charge can still verify. The account credential/TLS boundary remains trusted, and local binding, stable charge identity and search ambiguity checks remain mandatory. Capture sends the exact positive capture_amount. Existing local intent ownership checks remain mandatory; see [ADR-008](../Architecture/Decisions/ADR-008-omise-full-capture-context.md).

If both optional response fields are absent, verified signed creation context plus the strict successful/paid/authorized/unreversed/deferred/non-capturable/non-reversible/zero-refund state can confirm full capture. An explicit partial amount or pre_auth/conflicting type is never overridden. Missing context, forged/edited metadata, mismatched intent/amount/currency, unknown state or missing financial flags remains unknown. Restart and lost-reference recovery use only provider GET/search results and never create replacement charges or repeat paid capture.
