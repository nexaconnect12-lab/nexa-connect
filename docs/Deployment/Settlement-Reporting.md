# Settlement reporting rollout and recovery

Settlement original-event replay is now provided by [ADR-035](../Architecture/Decisions/ADR-035-audited-settlement-replay.md) and [the administrative runbook](../Deployment/Settlement-Replay.md). POS 23 adds two immutable audit tables; Reporting stays 22 and compatibility is 0.38.0 (201 tables, POS 52 / Reporting 19). Customer routes/permissions remain read-only; unknown original publication fields fail closed.

Deploy Reporting 22 with matching POS 23, BFF and portal binaries at compatibility 0.38.0; Order 19, Payment 18 and Authorization 15 stay unchanged. ADR-034 added no POS migration; ADR-035 now adds POS 23 replay audit storage. Reporting adds `settlement_facts` and `settlement_event_receipts`; immutable guards protect both and unique organization/settlement and organization/branch/day constraints protect business identity. Payloads retain the Reporting-owned model. Event, fact and projector checkpoint commit together. DDL belongs to the migration identity; runtime needs SELECT/INSERT on the two new tables and existing checkpoint SELECT/INSERT/UPDATE, plus existing inbox/outbox privileges where applicable. POS inventory needs SELECT on existing settlement state, commit decisions, receipts and outbox. No new identity role/grant, cross-database query or owner FK is introduced. Update the reviewed runtime grants after migration; do not run services with migration credentials.

Bind and verify the durable settlement queue before allowing new POS V2 commits. Configure Reporting `SettlementConsumer:Enabled=true`, `ConnectionString` with the broker secret, optional `Exchange` (default `nexaconnect.events`), `Queue` (default `nexaconnect.reporting.day-settlements.v1`) and `PrefetchCount` (default16, bounded1–100). The queue name is stable logical consumer vocabulary; bindings include **both** `pos.branch-day-settled.v1` and `pos.branch-day-settled.v2`. Dead-letter queue/routing key is the configured queue plus `.dead`. Enable the existing POS dispatcher with the same exchange and verify actual bindings, not startup alone. `Services:POS` and existing BFF Reporting address remain required. See the Reporting [.env.example](../../src/Services/NexaConnect.Services.Reporting/.env.example).

New publications are version2; old decided recovery keeps its original retained event. Never rewrite old V1 rows to add proof, republish under a new ID, reset dispatch flags or mutate a Reporting fact/hash. Before upgrade, retain backups and review in-flight consumers/contracts. New consumer readiness confirms initial binding/QoS/registration only, not ongoing health. Missing rows can mean disabled publication/consumption, queue absent during prior dispatch or transport/projection failure; observations never imply rollback or permission to resettle. Historical V1/V2 events dispatched before this queue existed can be recovered through the manifest-pinned [administrative original-event replay runbook](Settlement-Replay.md).

Exact redelivery/restart is idempotent. Conflicting or invalid events dead-letter; investigate original immutable source evidence and preserve both identities. Transient projection/connectivity failures retry. A commit-before-ack failure redelivers the same event without changing fact/checkpoint. Reporting 22→21 refuses any facts/receipts/settlement checkpoint history; empty rollback succeeds. Preserve original source history and use backup/forward recovery for retained evidence. Controlled general rebuild/export is not added.

Observability uses shared JSON/OTLP service names `nexaconnect-pos`, `nexaconnect-reporting`, and `nexaconnect-customer-bff`. Query safe `Settlement inventory`, `Settlement report`, `Settlement reporting BFF` or `Settlement financial` events and validated `CorrelationId`. Worker activity is `day-settlement.project`; metric `reporting.day_settlement.outcomes` labels applied/replayed/rejected/retry/connection_retry. Logs contain categories/validated identity only, never bodies, amounts, tokens/cookies, arbitrary headers, personal fields or private authorization metadata. Source/customer authorization remains live and failures clear portal values.

Verify with `scripts/test-settlement-reporting.ps1 -ConfirmDisposableInfrastructure`, the broader day-seal matrix, architecture/unit tests, frontend check/Vitest and `npm run test:e2e:settlement-reporting`. The genuine cashier cutoff gate now selects Reporting 22/0.38.0 and verifies actual V2 binding/publication, accountant read and protected portal ledger alongside its seventeen existing workflows. See [execution evidence](../Architecture/Evidence/Settlement-Reporting-Acceptance.md). These local checks do not certify production/remote CI, whole-current-day finalization or global delivery completeness.

The existing [day-seal verification workflow](../../.github/workflows/day-seal-verification.yml) includes the settlement unit/source-authorization/HTTP filters, dedicated PostgreSQL/RabbitMQ runner and ledger browser regression. It uploads only sanitized `verification.json` receipts from the day-seal and settlement-reporting runs; private runtime logs/configuration are excluded. This workflow is authored configuration; remote execution remains unverified.

## Settlement CSV export

Deploy matching Reporting, Customer BFF and Customer Portal binaries for the [export routes](../API/Settlement-Export.md). POS 23 / Reporting 22 / Authorization 15 and compatibility 0.38.0 remain applicable; no migration, environment variable, new workload client or expanded customer grant is required. Existing Reporting POS/Restaurant/Directory/Authorization and BFF Reporting/Directory HTTPS dependencies remain mandatory. Proxy rules must allow the GET `.../day-settlements/export.csv` suffix and attachment responses; do not enable caching. The 4 MiB export buffer is separate from the existing 2 MiB JSON limit. Use bounded request concurrency at deployment scale; large ranges can return 503 and should be narrowed.

Use End-of-day → Settlement ledger → Download settlement CSV. The operation checks current customer membership and Reporting/POS read permissions again and makes a fresh comparison. Import money/identity/date columns as text; sum only settlement rows and never add correction detail back into cash variance. A matched file records that exact selection at its observation times, not later delivery or global completeness. Revoked/expired access and source outages yield sanitized errors with no attachment. Nothing changes receipts, source barriers, revisions, dispatcher flags or Reporting facts. Retry with a fresh download after access/services recover; repair still uses the separately authorized replay procedure.

Service names remain `nexaconnect-reporting` and `nexaconnect-customer-bff`; query `{service_name="nexaconnect-reporting"} |= "Settlement report"` and `{service_name="nexaconnect-customer-bff"} |= "Settlement reporting BFF"`, narrowed by validated `CorrelationId`. Existing safe authorization/failure events cover export routes; logs must exclude CSV bytes, amounts and credentials.

Verification: `dotnet test tests/Unit/NexaConnect.UnitTests --filter "FullyQualifiedName~SettlementCsvTests|FullyQualifiedName~SettlementReportingTests"`; `dotnet test tests/Integration/NexaConnect.IntegrationTests --filter "FullyQualifiedName~SettlementExportHttpTests|FullyQualifiedName~CustomerSettlementReportsBoundaryTests"`; architecture tests; under `src/Frontend`, `npm run check`, `npm test -- apps/customer-portal/src/settlementReporting.test.ts apps/customer-portal/src/settlementExport.test.ts` and `npm run test:e2e:settlement-reporting`. The day-seal CI workflow includes these focused export filters and portal tests. HTTP tests use actual hosts with test authorization/source ports; browser tests intercept BFF responses. See [execution evidence and exclusions](../Architecture/Evidence/Settlement-Export-Acceptance.md); remote CI, production deployment/load and a new joined real-OIDC export run remain unverified.
