# Cash correction Reporting rollout and recovery

Apply Reporting `0021_cash_correction_facts` and POS `0021_cash_correction_replay` with application compatibility at least 0.35.0 before enabling the matching Reporting/POS/BFF/Portal binaries. Existing prerequisites remain Order 19, Payment 18 and Authorization 15. There is no new customer permission or limit configuration: posting retains ADR-031 mandatory limits; reads require current membership, `reporting.sales.read`, `pos.day-close.read` and `pos.cash-review.read`. The existing Reporting POS URL and customer bearer are used; no cross-owner database query is introduced.

Reporting runtime needs SELECT/INSERT on `cash_correction_facts` / `cash_correction_event_receipts` and existing checkpoint writes. Facts uniquely bind event and organization/correction/work/tender/Order. Facts and receipts reject UPDATE/DELETE/TRUNCATE; scope/posting-time index supports inventory. Migration identity owns DDL. POS runtime reads its ledger/outbox; replay has a separate administrative login with schema usage, SELECT on ledger/outbox and INSERT on `cash_correction_replay_runs` / `cash_correction_replay_attempts`. Audit readers need SELECT separately. Runtime/replay identities need no ledger mutation, foreign database access or trigger disabling.

Set `CashCorrectionConsumer__Enabled=true`, secret-managed `CashCorrectionConsumer__ConnectionString`, optional `Exchange` (default `nexaconnect.events`), `Queue` (default `nexaconnect.reporting.cash-corrections.v1`) and `PrefetchCount` (1–100, default 16). Default appsettings keep it disabled. Start the consumer and verify durable topic/main/dead queues, exact routing binding and consumer readiness before enabling POS outbox publication or replay. Invalid/conflicting events dead-letter; transient failures requeue. Event bodies, amounts, actor/Authorization details and credentials never enter logs.

Service `nexaconnect-reporting` provides `reporting.cash_correction.outcomes` statuses `applied`, `replayed`, `rejected`, `retry`, `connection_retry`, with safe `Cash correction financial` log categories and validated event correlation. HTTP logs use `Cash correction report`, POS uses `Cash correction inventory`, BFF uses `Cash correction reporting BFF`. Query `{service_name="nexaconnect-reporting"} |= "Cash correction"`; configure normal OTLP as for existing consumers. Initial `WaitUntilReadyAsync` proves first binding/registration only, not ongoing health or completeness.

## Administrative original-event replay

The existing `NexaConnect.CashCloseReplay` executable accepts a **first** `--cash-corrections` switch. Its separate mode needs `NEXACONNECT_CASH_CORRECTION_REPLAY_DB` (POS only), `NEXACONNECT_CASH_CORRECTION_REPLAY_BROKER`, and optional `NEXACONNECT_CASH_CORRECTION_REPLAY_EXCHANGE`. Inject secrets through the environment/secret store. Preview does not contact the broker. This is an administrative DB/broker boundary, not an OIDC/customer action. Operator UUID is asserted attribution; audit also retains authenticated PostgreSQL `session_user`. Controlled least-privilege login issuance is essential. JSON logs use `nexaconnect-cash-correction-replay`, with optional `OTEL_EXPORTER_OTLP_ENDPOINT`.

```powershell
dotnet build src/Tools/NexaConnect.CashCloseReplay
dotnet src/Tools/NexaConnect.CashCloseReplay/bin/Debug/net10.0/NexaConnect.CashCloseReplay.dll --cash-corrections --organization <uuid> --restaurant <uuid> --branch <uuid> --from 2026-10-01T00:00:00Z --to 2026-10-02T00:00:00Z --limit 1000
```

Preview emits only mode, manifest and count. Repeat the exact reviewed selection with `--execute --operator <uuid> --reason retry --manifest <SHA256>` (or `rebuild`). Times must end in `Z`; the closed posting range is at most 31 days. Excess candidates fail instead of truncating. Replay forwards the validated retained outbox JSON payload selected with ledger proof in the same repeatable-read snapshot; it does not serialize a replacement event. Original identities/correlation/time are retained; ledger, outbox flags and financial revisions stay unchanged. Durable intent/started/confirmed audit is append-only. An interruption yields a run ID when audit started; inspect it, make a fresh preview and replay original identities. Broker confirms prove routing to at least one subscriber, not Reporting projection; verify its binding and reload the live comparison afterward. The exchange broadcasts to all matching subscribers.

Stop the consumer and report reads before Reporting 21→20. It drops only correction facts/receipts/checkpoint; retain POS ledger/original outbox and replay after re-upgrade. POS 21→20 refuses any retained replay run; empty rollback is supported. Production retention must preserve original correction outbox evidence alongside the immutable ledger; losing an original prevents inventory/replay until legitimate history is restored. No source replacement event is invented.
