# Finalization preparation rollout and recovery

Deploy **Order 17 / Payment 16 / POS 16 / Authorization 12**, compatibility **0.31.0**, with matching Customer BFF/Portal and unchanged Reporting 20. POS 15 supplies its source fences; POS 16 supplies the coordinator. `scripts/migrate-databases.ps1` discovers these current targets. Stop affected old hosts while migrating/deploying; enable the coordinated routes only after all sources support the fence protocol. Mixed source binaries/schemas cannot certify prepared status.

No new secrets, environment variables or identity clients are introduced. Keep existing source/Reporting read permissions, service addresses, correlated HTTP clients and live Directory/Authorization access. Manager role defaults and existing-role backfill add `pos.day-close.finalization.prepare`; accountants/cashiers receive no default grant. Disable source and coordinator preparation/cancel routes before Authorization downgrade, which removes role links and overrides. Revoked managers can no longer resume; an authorized manager may cancel or wait for expiry.

Source-owned tables are `source_day_fences` and immutable `source_day_fence_audit`, each keyed by organization/operation; the audit also keys action. A partial window index supports active overlap checks. Only cancellation may update fence state; actor, window, approval/seal binding and expiry are immutable. Delete/truncate and cancellation reversal are rejected. Runtime roles need SELECT/INSERT on both tables, UPDATE(`cancelled`) on fence state and existing source revision/journal privileges including UPDATE(`fence_generation`). Scope/value SQL is parameterized. Restrict audit access and retain migration-only DDL privileges.

Each `source_financial_revisions` gains `fence_generation`. Revision zero is permitted only for a branch with a positive fence generation, so a fence can serialize an otherwise untouched branch without inventing financial activity. Source-managed triggers advance that control generation without a financial journal entry. Existing least-privilege revision reset/delete/epoch guards remain. Readiness summaries continue to use epoch/financial revision; generation is internal admission control.

POS adds `branch_day_finalization_preparations` (current version/state scoped by organization/restaurant/branch/date), immutable `branch_day_finalization_operations` (organization/operation fingerprint and exact command), and append-only `branch_day_finalization_audit` (day/version/action/actor/private Authorization decision ID/state). Projection FK binds existing approval state; preparation is persisted before HTTP and result/audit update atomically. Lock order is seal→approval→preparation, independent of source locks. No runtime HTTP runs inside a persistence transaction.

All new migrations refuse downgrade once source/coordinator history exists, including cancellation tombstones. Empty schemas can downgrade/reapply in reverse order; POS 16 must precede POS 15/14 removal. Use forward recovery after any retained operation. Never remove triggers/history to force rollback. Four-minute expiry automatically releases source admission without a cleanup worker; physical rows remain audit/replay history.

Recovery:

- On response loss/crash, load saved progress; wait for a 30-second claim to expire and resume the original actor/body operation. Source IDs and expiry stay fixed.
- On partial acquisition/cancellation, sources may differ temporarily. Retry exact intent; cancelled tombstones prevent late acquisition even at sources not initially reached.
- On stale/superseded approval, resolve source changes and explicitly recapture/reseal/reapprove as needed. Cancel or let the old lease expire before beginning against freshly reviewed approval/current coordinator version.
- On source permission revocation or outage, prepared proof clears. An authorized manager can cancel; otherwise the bounded source lease releases automatically.
- On a `financial_day_fenced` 409, the owning transaction has rolled back. Wait for cancel/expiry and recover through the owning idempotent workflow. POS settlement messages requeue with one-second fence-specific delay; do not acknowledge or discard them as permanent failures.
- Keep service/database clocks synchronized. A prepared observation reserves 15 seconds before nominal expiry; Portal additionally clears proof after 60 seconds. Future settlement finalization must perform its own durable source checks and cannot trust cached state.

Shared telemetry names: `nexaconnect-order`, `nexaconnect-payment`, `nexaconnect-pos`, `nexaconnect-customer-bff`. Search `Finalization preparation`, `Financial day fence` and validated `CorrelationId`. POS worker outcome `fenced_retry` is safe structured telemetry. Never log financial/audit bodies, tokens, cookies, arbitrary headers or actor details.
