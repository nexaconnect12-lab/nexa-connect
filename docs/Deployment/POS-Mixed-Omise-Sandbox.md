# Omise sandbox alongside manual POS payments

29 October 2026: source implementation adds sandbox card checkout to the same local POS
application as cash/manual PromptPay and QR collection. Default profiles remain manual;
the retained pilot has not been activated for Omise or certified by a fresh provider test.
This is not production card collection or a physical card-reader integration.

## Cashier workflow

An enabled profile shows **Checkout → Checkout payment → Omise sandbox card — test only**
beside **Cash / manual PromptPay**. The configured manual method remains the default.
The selection is window-local, resets to the configured default when no operator is signed
in, and cannot change a retained checkout/payment. The original method is saved with the
existing pending checkout before sending. Restart restores that method; do not disable the
capability or change scope to work around retained card recovery.

Select card before confirming the quote. Use a fresh single-use token generated by the
[HTTPS test helper](../../src/Tools/NexaConnect.OmiseTokenHelper/README.md); no PAN/CVV or
provider keys belong in POS. The masked token is sent transiently, never saved. Changing
methods, manual/QR recovery, lock and sign-out clear it. Uncertain card orders use the
original Order and tokenless verification unless the server explicitly asks for a new token.
Card orders cannot use the manual Paid action. A provider failure must never lead to a
replacement cash order without original-state reconciliation.

QR collection remains cash/manual PromptPay even if card is selected for a new walk-up
order. Omise card collection for existing QR orders is not introduced. Existing live owning
permissions, tenant isolation, settlement idempotency, provider recovery and correlation
telemetry still apply. No new financial route, permission, event or database migration.

## Operator setup and activation

There is no cashier-facing enable switch or secret-key field. Backend setup is an operator
operation, not authority granted by the payment picker. Keep defaults disabled until ready.

1. Finish/reconcile active work, close POS and stop its owned QR edge/stack through the
   existing lifecycle tools. Preserve the run, scope, certificates, databases and recovery.
2. In a local PowerShell terminal, inject a test key without putting it in shell history or
   chat. Resolve the existing retained run ID from the current local pilot record:

   ```powershell
   $maskedOmise = Read-Host 'Omise TEST secret' -AsSecureString
   $env:NEXACONNECT_OMISE_TEST_SECRET_KEY = [Net.NetworkCredential]::new('', $maskedOmise).Password
   $maskedOmise.Dispose()
   $omisePilotRun = (Get-Content .runstate/qr9-current.json -Raw | ConvertFrom-Json).runId
   try {
       pwsh -NoProfile -File scripts/first-draft-stack.ps1 -Action Validate -EnableOmiseTestCheckout
       if ($LASTEXITCODE -ne 0) { throw 'Sandbox validation failed.' }
       pwsh -NoProfile -File scripts/first-draft-stack.ps1 -Action Start -RunId $omisePilotRun -EnableOmiseTestCheckout -ConfirmTestResources
       if ($LASTEXITCODE -ne 0) { throw 'Sandbox startup failed; preserve the retained run.' }
   } finally {
       Remove-Item Env:NEXACONNECT_OMISE_TEST_SECRET_KEY -ErrorAction SilentlyContinue
   }
   ```

   Use only an Omise test-account key. Live keys, whitespace and invalid key formats are
   rejected. Activation requires stopped services and a build-enabled Start; NoBuild/Restart
   cannot first enable it. The Boolean capability is retained in `state.json`; the test secret
   is retained only in the existing current-user Windows DPAPI `secrets.clixml`. State/client
   settings/manifests contain no key. Only Payment receives it as explicit service configuration.
   Omise input environment aliases are removed before Docker/build subprocesses and service
   startup; service hosts also scrub inherited development secrets. Credential rotation is a
   separate recovery operation; the enable command rejects replacement of an existing key.
3. Existing enabled profiles inherit the capability/DPAPI credential on normal Start/Restart
   without another environment key. There is no implicit downgrade when the switch is omitted.
   Order enables its existing test-card workflow; Payment selects official Omise HTTPS and
   existing authorization/capture/refund recovery. Existing binding-first outbox startup and
   Order reconciliation remain in force. External webhooks remain disabled, as before.
4. Complete normal source/candidate validation, prepare a fresh QR activation binding and
   package/install the matching POS. Capability addition leaves the configured manual default,
   scope and isolated recovery location unchanged. Never edit an installed signed/hash-bound
   release or copy a key into its settings. The hosted installer remains manual-only.
5. Sign in, open a shift, test a cash order and QR collection, then select sandbox card for
   a separate test cart. Verify original Order/Payment identity, capture and amount in the
   matching test dashboard, tokenless recovery, receipt and no duplicate charge. Test lock,
   restart and network interruption using the existing [acceptance procedures](Omise-POS-Card-Token-Handoff.md).

The same application supports both paths; local staging still requires controlled service
refresh and a matching package. Selecting card alone cannot activate Payment or certify
credentials/account ownership. Existing historical Omise evidence is not a fresh mixed-mode
acceptance pass. Provider/real OIDC/POS/phone/physical device and production acceptance remain
separate. In particular, legacy card checkout does not establish a persisted card Order-to-
shift link or certify branch day-close/settlement of card receipts.

## Observability and verification

Existing `nexaconnect-pos-client` checkout transport, `nexaconnect-order` and
`nexaconnect-payment` safe correlation events are reused; filter by service, original
correlation and operation (`order.quote`/`order.place`). Never log keys, tokens, payment bodies,
card details or provider references. No new cross-service adapter or background worker.

Tests cover additive capability/defaults, unchanged storage, unsupported/remote configuration,
retained method validation, card-token transport/clearing, original-order verification and QR
manual separation. `scripts/test-first-draft-omise-guards.ps1` checks lifecycle/secret isolation
and package guards without infrastructure/provider access. It is required by the QR6 candidate
gate. WPF tests use synthetic identity/HTTP; no provider charge or live activation is implied.
See [ADR-053](../Architecture/Decisions/ADR-053-additive-local-omise-sandbox.md).
