# Catalog menu organization storage

Catalog migration7 (`0007_menu_organization`) requires minimum application compatibility0.42.0 and adds two tables: `catalog_menu_organizations` and `catalog_menu_organization_audit`. Catalog now has29 tables; the full13-service catalog has219. Other service schemas are unchanged; standalone migration default remains0.38.0, so explicitly supply0.42.0 for this target. The retained pilot launcher derives the highest compatibility dynamically.

The organization/branch composite key owns a versioned JSON category/placement snapshot. Shape/count checks support the Domain invariants; the Domain validates trimmed unique names, IDs, category references and product membership. There is no cross-service FK or shared table. Product IDs are Catalog references validated against a tenant/branch-leading, ordered `FOR SHARE` menu query inside the same transaction (201-row overflow sentinel). Concurrent product insertion is safe: unplaced new products default to Uncategorized; referenced existing products remain locked through the save.

A transaction-scoped advisory lock derived only from parameterized organization/branch values serializes the absent first layout as well as later saves. The Domain expected-version decision controls mutation/no-op. The upsert also predicates updates on the previous version. Layout, detailed previous/current JSON audit and `PlatformAuditEventV1` generic `catalog.audit.v1` outbox (`catalog-menu-organization`) commit atomically. No price-change event is emitted. Audit scope/version is unique; update/delete triggers enforce immutable history. Runtime default table grants must cover both new Catalog tables; no cross-database access or new permission is needed.

Category reordering/renaming/unassignment does not change menu prices, availability, quote fingerprints, image approval, order/financial rows, inventory or provider state. Deleting a category never deletes products or images. Reads filter stale placements for products no longer in the live menu; the next explicit authorized save may audit their removal.

Empty7→6→7 is supported. Retained layout or audit history blocks downgrade; use forward recovery. Do not remove audit or reset versions to force rollback. In-memory mode is non-durable and emits no outbox. Back up Catalog before rollout and preserve all other owning data and Windows protected recovery.

`MenuOrganizationPersistenceTests` uses only the generated local QR PostgreSQL fixture. It covers first-write races, tenant/branch isolation, foreign products, no-op and stale proof, atomic rollback when outbox is unavailable, immutable audit, empty downgrade/reapply, populated downgrade refusal and unchanged prices/price-event count. Run via `scripts/test-qr-entry-persistence.ps1 -ConfirmDisposableInfrastructure`; cleanup remains mandatory.
