# Financial portal acceptance fixture

The [joined cashier-to-day-close gate](../../../docs/Deployment/Cashier-Day-Close-Acceptance.md) implements real cashier PKCE, authorized shift/cash/checkout/manual-settlement/receipt/review commands, actual Order→POS/Reporting publication and Customer Portal preparation with manager contention and POS restart. Its reference-only fixture seeds no financial transitions. An acceptance-only host injects historical command time into actual Order/POS applications; production uses the system clock with no configurable clock switch. Five browser scenarios, six Authorization persistence cases and verified cleanup are required; execution evidence remains separate from production settlement/cutoff certification.

Preparation mode additionally requires `DAY_CLOSE=1`, `END_OF_DAY=1`, `SECOND_MANAGER_SUBJECT` distinct from the accountant/first manager, and run-owned POS fixture IDs. Its guarded commands add `resolve-day-close`, `same-total-evidence`, `late-cash`, `approve-cash`, `preparation-proof`, `stop-pos`, `start-pos`, `revoke-day-close-read`, `revoke-day-close-prepare`, `revoke-manager-source`, `restore-manager-source` and `membership-second`. Closure/review/late-cash actions use owning POS repositories with synthetic source authorization/event outcomes; only preparation uses the real Customer BFF/POS command boundary. `same-total-evidence` saves the completed Order through its owning repository, advancing metadata/version while preserving financial receipt/publication content; it does not create a second financial event. Process actions write bounded run-scoped requests to the launcher, never accept a PID or executable. Proof privately validates real granted preparation audit decision IDs and returns only state/count/lease metadata. Use the [joined preparation launcher](../../../scripts/test-day-close-portal.ps1) and [scope/recovery runbook](../../../docs/Deployment/Day-Close-Portal-Acceptance.md); no production host loads this fixture.

The [end-of-day launcher](../../../scripts/test-end-of-day-portal.ps1) reuses this tool with `NEXACONNECT_FINANCIAL_PORTAL_END_OF_DAY=1` and an additional exact run-owned `DB_POS`. It provisions yesterday in Asia/Bangkok. Optional repository `TimeProvider` inputs keep synthetic Payment creation/capture/refund timestamps historical and consistent; production defaults to the system clock and offers no environment clock switch. Order creation time is set only while unpaid and before receipt/publication retention. POS fixture Infrastructure inserts fresh historical snapshots into an empty owned database, with required authorization identifiers and parameterized data; it does not rewrite existing evidence or disable triggers. `revoke-source` is allowed only in end-of-day mode and denies the accountant's active `payment.refund.read`. See [fixture semantics and exclusions](../../../docs/Deployment/End-Of-Day-Portal-Acceptance.md).

Standalone test-only fixture for the [joined runner](../../../scripts/test-financial-completeness-portal.ps1). Commands are `provision`, `record`, `deliver`, `revoke` and `membership`. Require `NEXACONNECT_FINANCIAL_PORTAL_ENABLED=1`, `CONFIRM_DISPOSABLE=1`, a generated 32-hex `RUN_ID`, two distinct UUID subjects (`READER_SUBJECT`, `RESOLVER_SUBJECT`) and a run-scoped `STATE_PATH` ending in `<run-id>/fixture.json`.

The launcher injects `DB_PLATFORM`, `DB_RESTAURANT`, `DB_AUTHORIZATION`, `DB_ORDER`, `DB_PAYMENT`, `DB_REPORTING` under the same prefix. Each connection must use IPv4 loopback and its exact `nexa_review_it_<run-id>_<suffix>` database without a custom search path. `BROKER` must be loopback AMQP; `RECOVERY_DLL` must resolve to the repository's fixed Debug recovery executable. Use only the launcher, never an existing environment.

Provisioning uses owning Platform Directory/Restaurant/Authorization Application services, Order aggregate/repository and Payment intent/refund repositories. Synthetic successful provider outcomes bypass external payment I/O; this does not test checkout/refund HTTP or provider acceptance. It retains original financial source evidence and waits until a minute-aligned window is closed. A second provision refuses existing state/source data.

`record` invokes the real financial recovery CLI with `--record`, preserving source state and operator attribution. `deliver` uses real source outboxes and RabbitMQ dispatchers, waits for actual Reporting fact consumption and removes its temporary event sink. It does not write report facts. Fixture-only Infrastructure changes the accountant's existing active sales-permission override to deny; membership suspension uses the owning Platform Directory Application service. Financial source operations remain owning transactions and no distributed snapshot is claimed.

Execution is bounded to three minutes; spawned recovery children are terminated on timeout. Failure diagnostics contain bounded stage/type/SQLSTATE only. The launched HTTP service hosts do not inherit the runner's `NEXACONNECT_*` fixture/admin settings; their required service configuration is injected explicitly. State holds generated scope IDs and timestamps, not bearer credentials or financial bodies. Reporting telemetry remains on the actual host. See [scenario matrix and evidence requirements](../../../docs/Deployment/Financial-Completeness-Portal-Acceptance.md).

Cashier mode requires `CASHIER_DAY_CLOSE=1`, `DAY_CLOSE=1` and `END_OF_DAY=1` under the normal fixture prefix. `provision-cashier` creates reference-only store/hierarchy/access state and run-owned `clock.json`; `cashier-proof` returns only verified singleton counts and Authorization verification. `host-order`/`host-pos` run actual entry points through the test-only Kestrel host and require `Acceptance__ConfirmDisposable=1`, a valid `Acceptance__RunId`, the exact run-owned `Acceptance__ClockPath`/database/realm and a loopback `Acceptance__Port`. Historical time must precede current time and be within three days. These host-only settings are not production service options. `tests/Scripts/Test-CashierDayCloseHostPreflight.ps1` separately covers eight preflight rejection cases without starting infrastructure; build the fixture before invoking it.
