# Customer Service

Owns organization-scoped customer profiles. `POST /api/customer/v1/organizations/{organizationId}/customers` and `GET /api/customer/v1/organizations/{organizationId}/customers/{id}` provide the initial customer profile slice. Set `Persistence:Provider=PostgreSQL` and `ConnectionStrings:Customer` to use the parameterized PostgreSQL repository; development defaults to the in-memory adapter. Contacts, addresses, loyalty projections, and profile status transitions remain follow-up work.

Customer calls require the protected organization context to equal the route organization, active Platform Directory membership with enabled `nexa_connect` access, and `customer.profile.create` or `customer.profile.read`. Undocumented workload identities do not bypass this boundary. Reads always filter by both `organization_id` and profile ID; tenant mismatches return `404`.

Use the service-specific [`customer.production.env.example`](../../../docs/Deployment/customer.production.env.example) for production configuration. PostgreSQL creation uses normalized `(organization_id, customer_number)` as its idempotency boundary. A matching retry returns the existing profile without new audit/events; materially different reuse or an identity-subject collision returns `409`. Migration 1 owns the outbox. Migration 2 adds append-only Customer audit that excludes profile fields. A first creation atomically commits the profile, `customer.profile-created.v1`, and `customer.audit.v1`; event/audit payloads contain identifiers, status, version, actor, and outcome but no name, profile identity subject, contacts, addresses, or preferences. Audit actor subjects are restricted pseudonymous accountability identifiers; production must restrict audit access and define retention/archive under the approved audit policy because no automated purge is implemented. Deploy Reporting migration 6 before enabling `Outbox__Enabled` with a secret-managed `Outbox__ConnectionString`.

Structured logs use service name `nexaconnect-customer`; correlation IDs propagate to Platform Directory and Authorization and are preserved in Customer outbox metadata. Safe boundary events are `Customer authorization denied`, `Customer organization access lookup failed`, and `Customer organization access dependency failed`; query them by service name and `CorrelationId` without logging subjects, tokens, or profile fields. Six coordinated Customer/Reporting acceptances passed locally against PostgreSQL 17 and RabbitMQ, including concurrency, atomic rollback, confirmed publication, replay, and the actual 0→2→1→2 runner.
JSON stdout is always enabled. Enable OTLP with `Observability__OtlpEnabled=true`; use the [observability guide](../../../docs/Deployment/Observability.md) for the endpoint and queries.
