# Payment Service

Owns payment intents and idempotency keys. `POST` and `GET /api/payment/v1/intents` provide the first payment-intent API. Every request requires `X-Nexa-Organization-Id`; only the `nexaconnect-order-service` trusted workload may bypass customer authorization, and other globally trusted workloads are denied by Payment. Order propagates server-owned organization/restaurant/branch context and customer calls additionally use the protected application context. Set `Persistence:Provider=PostgreSQL` and `ConnectionStrings:Payment` to use organization-leading persistence; development defaults to the non-durable in-memory adapter. Reusing an organization/restaurant idempotency key returns the original intent only when the normalized request matches and otherwise returns `409`.

Customer Portal payment-intent calls carry the shared tenant context. Payment validates Platform Directory access, referenced Order ownership, Restaurant scope, and `payment.intent.create` or `payment.intent.read`. Cross-tenant reads return `404`. Configure Platform Directory, Order, Restaurant, Authorization, and workload credentials.

Payment migration 1 owns the outbox. Migration 2 adds `organization_id`, append-only `payment_audit_records`, and tenant-leading intent lookup. A new PostgreSQL intent atomically commits `payment.intent-created.v1`, `payment.audit.v1`, and local audit; an idempotent replay publishes nothing. Enable dispatch with `Outbox:Enabled=true` and secret-managed `Outbox:ConnectionString`. The destructive migration-2 downgrade removes organization attribution and audit history but preserves intents and outbox rows, so disable producers and drain dispatch before rollback.

Migration 2 marks pre-existing intents with the empty organization UUID because Payment cannot infer ownership from its database. Before deploying the migration-2 application or enabling dispatch, backfill every sentinel row from Order-owned organization data through a reviewed operational reconciliation and verify none remain. Before downgrade, verify no `(restaurant_id,idempotency_key)` is used by multiple organizations; the downgrade fails safely until collisions are reconciled.

All five opt-in Payment acceptances plus Reporting vocabulary persistence passed locally against PostgreSQL 17 and RabbitMQ. Live coverage proves atomic rollback, cross-tenant lookup, concurrent/conflicting idempotency, append-only audit, confirmed publication over a new recovery connection, mechanical legacy backfill, downgrade collision refusal, and the actual migration runner's 0→2→1→2 lifecycle. Unit coverage proves exact Order-workload restriction and bounded financial/actor values. Unconfigured cases are reported as skipped. Established-dispatcher reconnection is not covered. `IPaymentProvider` remains the unused provider boundary; authorization, capture, refunds, provider transaction persistence, and reconciliation are not enabled by this slice.

Structured logs use service name `nexaconnect-payment`; correlation IDs propagate to Platform Directory, Order, Restaurant, and Authorization.
JSON stdout is always enabled. Enable OTLP with `Observability__OtlpEnabled=true`; use the [observability guide](../../../docs/Deployment/Observability.md) for the endpoint and queries.
