# Payment Service

Owns payment intents, provider authorization state, and idempotency keys. `POST /api/payment/v1/intents`, `POST /api/payment/v1/intents/{id}/authorize`, and `GET /api/payment/v1/intents/{id}` provide the implemented payment boundary. Every request requires `X-Nexa-Organization-Id`; only the exact `nexaconnect-order-service` workload can invoke authorization. Other globally trusted workloads are denied. Order propagates server-owned organization/restaurant/branch context and customer create/read calls additionally use the protected application context. Set `Persistence:Provider=PostgreSQL` and `ConnectionStrings:Payment` to use organization-leading persistence; development defaults to the non-durable in-memory adapter. Reusing an organization/restaurant idempotency key returns the original intent only when the normalized request matches and otherwise returns `409`.

Customer Portal payment-intent calls carry the shared tenant context. Payment validates Platform Directory access, referenced Order ownership, Restaurant scope, and `payment.intent.create` or `payment.intent.read`. Cross-tenant reads return `404`. Configure Platform Directory, Order, Restaurant, Authorization, and workload credentials.

Payment migration 1 owns the outbox. Migration 2 adds `organization_id`, append-only `payment_audit_records`, and tenant-leading intent lookup. Migration 3 adds authorization state and migration 4 adds recoverable lease ownership, bounded attempts, and reconciliation timestamps. Reporting migrations 8 and 9 must be applied before authorization publication. A new intent and each authorization transition atomically commit local audit plus versioned lifecycle and `payment.audit.v1` outbox messages. The provider call occurs after the start transaction commits and before a separate result transaction; no database transaction spans network I/O. Enable dispatch with `Outbox:Enabled=true` and secret-managed `Outbox:ConnectionString`.

Migration 2 marks pre-existing intents with the empty organization UUID because Payment cannot infer ownership from its database. Before deploying the migration-2 application or enabling dispatch, backfill every sentinel row from Order-owned organization data through a reviewed operational reconciliation and verify none remain. Before downgrade, verify no `(restaurant_id,idempotency_key)` is used by multiple organizations; the downgrade fails safely until collisions are reconciled.

Authorization uses the payment-intent ID as the stable provider request identity. One caller atomically acquires the authorization lease; concurrent/replayed calls observe `authorizing` or the terminal result without a second provider call. Only sanitized provider references and allow-listed machine failure categories are retained. Provider response bodies, PAN, CVV, tokens, and secrets must never enter persistence, events, audit, or logs. A timeout or unavailable provider is recorded as `unknown`, not failed. The hosted recovery worker reclaims expired leases using PostgreSQL row locks, looks up provider status with the stable Payment intent ID, and atomically records `authorized`, `failed`, or `requires_action`. Exhausted attempts move to `requires_action` for operator review.

The immediate-capture boundary adds Order-only `POST /api/payment/v1/intents/{id}/capture`. Only `authorized` can move to `capturing`; provider I/O occurs outside the database transaction, and a separate transaction records `captured`, `failed`, or `capture_unknown` with safe audit and outbox events. Order becomes paid only for `captured`; uncertain capture remains payment-pending without Inventory/Kitchen compensation. Provider capture references are internal. Capture uses the Payment intent ID as `Idempotency-Key`, so the configured provider must enforce stable replay semantics across transport retries.

Payment migration 6 adds capture-specific recovery leases, bounded attempts, and reconciliation timestamps. The PostgreSQL-only recovery worker claims expired `capturing` and `capture_unknown` intents, calls the provider status endpoint without holding a database transaction, and transactionally records `captured`, `failed`, `capture_unknown`, or `requires_action` plus `PaymentCaptureReconciledV1` and `payment.audit.v1`. It never repeats the capture command. Only an explicit provider `captured` result completes Order; explicit failure triggers Order-owned idempotent Inventory/Kitchen compensation, while unknown or exhausted outcomes retain the order for review. Apply Reporting migration 11 before enabling recovery publication. Configure `PaymentProvider__CapturePath`, `PaymentProvider__CaptureStatusPath`, `PaymentProvider__LeaseDuration`, `PaymentProvider__MaximumCaptureRecoveryAttempts`, and `PaymentProvider__RecoveryInterval`.

The default build and test suite covers authorization, capture success/replay, capture uncertainty and reconciliation, bounded recovery, illegal pre-authorization capture, Order HTTP capture, contract serialization, and migration catalog changes. Fourteen coordinated opt-in PostgreSQL 17/RabbitMQ 4 cases passed locally on 2026-08-26, including Payment `0→6→5→6`, Order `0→2→1→2`, Reporting migration-11 replay, persisted restart recovery, and transactional outbox rollback. Focused automated coverage separately proves duplicate-terminal delivery and partial-compensation retry. Production-provider delayed/dropped responses and process termination, automatic recovery of an established dispatcher connection, production alert delivery, and release-environment rollback/forward-recovery rehearsal remain gates. Delayed capture policy, void, refunds, and settlement reconciliation remain planned.

Structured logs use service name `nexaconnect-payment`; correlation IDs propagate to Platform Directory, Order, Restaurant, and Authorization.
JSON stdout is always enabled. Enable OTLP with `Observability__OtlpEnabled=true`; use the [observability guide](../../../docs/Deployment/Observability.md) for the endpoint and queries.
Capture recovery also exports claim, outcome, and failure counters through meter `nexaconnect-payment`. Operational thresholds and safe recovery procedures are documented in the [capture-recovery runbook](../../../docs/Deployment/Payment-Capture-Recovery-Runbook.md).
