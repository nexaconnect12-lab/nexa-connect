# Order Service

The Order bounded context owns order aggregates, line price snapshots, status transitions, and the first restaurant sales workflow.

`Application/Workflow/PlaceOrderWorkflow.cs` coordinates the bounded-context ports in this order:

`Catalog/Menu → Order → Inventory reservation → Kitchen ticket → Payment authorization`

The workflow publishes versioned contracts from `NexaConnect.Contracts.IntegrationEvents` after each accepted step. PostgreSQL mode persists the aggregate, immutable line snapshots, idempotency record, and integration event in one transaction; the shared outbox dispatcher delivers events to RabbitMQ. The public endpoint is `POST /api/order/v1/workflows/place` and requires an idempotency key. Outbound adapters attach a configured development token or obtain a short-lived Keycloak client-credentials token. A provider timeout or unavailable response leaves the order `payment_pending` and retains Inventory/Kitchen work. When `PaymentReconciliationConsumer:Enabled=true`, the durable inbox consumer subscribes to authorization, capture, and void lifecycle/reconciliation events. Every reconciliation must match the persisted organization and payment-intent ID. Authorization alone never completes an order. Confirmed capture marks it paid; confirmed void performs retry-at-least-once Inventory/Kitchen compensation and records payment failure, so dependencies must deduplicate by order identity. `void_unknown` retains work, while `void_failed` and exhausted recovery move the order to `payment_review` and publish `order.payment-review-required.v1`; this slice includes no downstream consumer. Paid orders ignore void events because post-capture reversal belongs to refunds. Order migration 2 owns the durable inbox and pending state; migration 3 adds unique organization/payment-intent ownership, `payment_review`, and downgrade guards. Legacy organization values and pending-order payment-intent values are nullable for migration compatibility and must be authoritatively backfilled from Order/Payment evidence before access, which fails closed when either value is absent. Downgrade is unsupported after migration-3 ownership is persisted.

Payment-review operations require authentication and PostgreSQL migration 4. `GET /api/order/v1/payment-reviews?organizationId={id}&branchId={id}` lists open cases, `GET /api/order/v1/payment-reviews/{orderId}?organizationId={id}` reads one, and `POST /api/order/v1/payment-reviews/{orderId}/resolve` accepts organization, resolution, reason, expected concurrency version, and optional correlation ID. Resolutions are `confirm_void`, `resume_payment`, and `escalate`. Dedicated `order.payment-review.read`/`order.payment-review.resolve` authorization is mandatory. Each decision atomically advances concurrency, appends immutable history, updates Order when applicable, and publishes `order.payment-review-resolved.v1` plus `order.audit.v1`. Open review count and oldest age are exported as `order.payment_review.open` and `order.payment_review.oldest_age_seconds`. Migration 4 cannot be downgraded after any case/history exists; use forward recovery.

For release verification, inject disposable Order/Reporting database settings, a disposable PostgreSQL administrator connection, and an isolated RabbitMQ URI, then run `scripts/test-payment-review-operations.ps1` with its three explicit confirmation switches. The four-case matrix proves migration rollback/forward guards, Reporting-13 removal/replay, repository-produced required/resolved/audit payloads surviving a failed hosted dispatcher and publishing persistently after worker restart, hosted Reporting projection with inbox duplicate suppression, and firing/resolved delivery through the isolated Alertmanager receiver. It does not certify a full broker-container restart, a production receiver, or a production threshold.

Resolution claims use a two-minute PostgreSQL lease, advance the concurrency version, and carry an opaque fencing token. Active `resolving` cases are visible by direct read but omitted from the open list; after expiration they appear open and only the same resolution may take over. Final commit must match the fencing token, and the retained Authorization decision ID is written with history/event state. Failed dependency calls release the claim; a process loss relies on expiry. Confirm-void retries can repeat idempotent compensation by Order identity.

The service also exposes `POST` and `GET /api/order/v1/orders` for the aggregate slice, plus the public place-order workflow endpoint. Production provider credentials and migration execution remain operational follow-up work; the deployed Kitchen ticket create/cancel API is now part of the workflow boundary.

Customer Portal create, read, and workflow requests are revalidated inside Order: Platform Directory confirms organization access, Restaurant confirms branch ownership, and Authorization evaluates `order.create`, `order.read`, or `order.place`. Request organization IDs must match the protected context. Cross-tenant reads return `404`; commands fail before the workflow executes.

Structured logs use service name `nexaconnect-order`; correlation IDs propagate through tenant checks and registered workflow HTTP adapters.
JSON stdout is always enabled. Enable OTLP with `Observability__OtlpEnabled=true`; use the [observability guide](../../../docs/Deployment/Observability.md) for the endpoint and queries.

In PostgreSQL mode, the `nexaconnect-order` meter reports pending payment-reconciliation inbox work, the oldest expired processing lease, unpublished outbox count/age, and gauge-collection failures. A collection failure means prior gauge samples may be stale. `OperationalMetrics:PollInterval` defaults to 30 seconds. The instruments contain no tenant, order, payment, or message labels. RabbitMQ queue and dead-letter depth are exported by the broker's Prometheus plugin in the local stack.

The migration acceptance executes Order `0→3→2→3` in a generated disposable database and proves `payment_review` blocks downgrade. Unit coverage proves confirmed-void compensation, uncertainty retention, financial-review transition, tenant rejection, and paid-order protection. Live RabbitMQ void replay, deployed dependency compensation, concurrency, and live-traffic rollback remain follow-up work.
