# Order Service

Order's `nexaconnect-order-service` workload token must include the `nexaconnect-api` audience for downstream authorization-scope calls. The checked-in realm and `scripts/test-keycloak-realm.ps1` enforce this desired configuration; startup import does not update an existing realm. If Restaurant returns `401`, apply the audience mapper through Keycloak administration and restart Order to clear its in-memory workload-token cache. The HTTP workflow adapters also require `Authentication:TokenEndpoint`, `ClientId`, and secret-managed `ClientSecret`; the checkout launcher derives the endpoint from Keycloak discovery so local HTTP identity is not accidentally contacted over HTTPS. Retain ambiguous POS checkout state and use **Verify original order** after repair; see [cashier recovery guidance](../../../docs/Deployment/POS-Cashier-Acceptance.md). A successful direct authorization-scope probe does not establish complete checkout acceptance.

Manual tender support models the Bangkok MVP methods `cash` and `promptpay_manual`. `POST /api/order/v1/orders/{orderId}/manual-settlement` requires branch-scoped `order.manual-payment.confirm` and an authenticated user subject. Order migration 5 atomically commits the Paid transition, one immutable settlement, `order.manual-tender-settled.v1`, and safe audit. Exact-total THB, tenant/branch, eligible-state, terminal, idempotency, and provider-exclusion rules are enforced in domain and persistence. PromptPay requires receipt confirmation; cash rejects bank references. Matching replay returns the original settlement while changed-payload reuse conflicts. Placement values `cash_manual` and `promptpay_manual` intentionally stop at KitchenAccepted without provider I/O; the WPF Paid control then submits the settlement, and the POS consumer projects the safe event idempotently.

For isolated local Payment Review verification, run `scripts/test-payment-review-isolated.ps1 -ConfirmDisposableInfrastructure`. It creates a new PostgreSQL/RabbitMQ/alert Compose project, runs the 13-case matrix and removes only that project's resources; no existing application connection settings are needed. The [live browser suite](../../Frontend/e2e/payment-review-live/README.md) separately requires running real Order and dependencies with fresh marked fixtures and dedicated OIDC accounts.

The Order bounded context owns order aggregates, line price snapshots, status transitions, and the first restaurant sales workflow.

Order migration 6 persists the original workflow payment method and correlation ID and adds a fenced claim/lease for checkout recovery. Migration 7 schedules every persisted checkout method through exact `submitted` and `inventory_reserved` state and provider methods through `kitchen_accepted`. When `WorkflowRecovery:Enabled=true`, the hosted worker replays Inventory reservation and Kitchen ticket creation with the original Order identity. For a provider method it then creates or reloads the Payment intent with stable idempotency key `order:{orderId}`. It authorizes only `pending`, captures only `authorized`, completes an existing `captured` intent, and never replays `authorizing`, `unknown`, `requires_action`, `capturing`, or `capture_unknown`. Uncertain outcomes bind the intent to `payment_pending`; the Payment recovery workers and Order `PaymentReconciliationConsumer` own the remaining transition. Exhausted authorization or capture becomes `payment_review`; a definitive failure performs idempotent Inventory release and Kitchen cancellation before committing PaymentFailed. Each accepted transition and integration-event enqueue commits atomically under the claim; foreground writes respect that claim and cannot regress a newer recovery stage. Dependency failures release the claim with a bounded retry delay; expired claims are reclaimable after process interruption. The retained correlation ID scopes recovery logs and propagates to downstream HTTP calls. Manual cash and PromptPay stop at `kitchen_accepted` for cashier verification and Paid confirmation. Legacy `accepted` rows remain readable as KitchenAccepted but are not reconstructed into a more precise prior stage.

`Application/Workflow/PlaceOrderWorkflow.cs` coordinates the bounded-context ports in this order:

`Catalog/Menu → Order → Inventory reservation → Kitchen ticket → Payment authorization`

The workflow publishes versioned contracts from `NexaConnect.Contracts.IntegrationEvents` after each accepted step. PostgreSQL mode persists the aggregate, immutable line snapshots, idempotency record, and integration event in one transaction; the shared outbox dispatcher delivers events to RabbitMQ. The public endpoint is `POST /api/order/v1/workflows/place` and requires an idempotency key. Outbound adapters attach a configured development token or obtain a short-lived Keycloak client-credentials token. Order supplies its organization/application tenant context to Inventory reservation and release calls so trusted workload authentication still selects Inventory's tenant-scoped persistence. Inventory `5xx` responses raise a dependency failure and their bodies are not persisted as business rejection reasons; a bounded non-success response below `500` remains a definitive reservation rejection. A provider timeout or unavailable response leaves the order `payment_pending` and retains Inventory/Kitchen work. When `PaymentReconciliationConsumer:Enabled=true`, the durable inbox consumer subscribes to authorization, capture, and void lifecycle/reconciliation events. Every reconciliation must match the persisted organization and payment-intent ID. Authorization alone never completes an order. Confirmed capture marks it paid; confirmed void performs retry-at-least-once Inventory/Kitchen compensation and records payment failure, so dependencies must deduplicate by order identity. `void_unknown` retains work, while `void_failed` and exhausted recovery move the order to `payment_review` and publish `order.payment-review-required.v1`; this slice includes no downstream consumer. Paid orders ignore void events because post-capture reversal belongs to refunds. Order migration 2 owns the durable inbox and pending state; migration 3 adds unique organization/payment-intent ownership, `payment_review`, and downgrade guards. Legacy organization values and pending-order payment-intent values are nullable for migration compatibility and must be authoritatively backfilled from Order/Payment evidence before access, which fails closed when either value is absent. Downgrade is unsupported after migration-3 ownership is persisted.

Payment-review operations require authentication and PostgreSQL migration 4. `GET /api/order/v1/payment-reviews?organizationId={id}&branchId={id}` lists open cases, `GET /api/order/v1/payment-reviews/{orderId}?organizationId={id}` reads one, and `POST /api/order/v1/payment-reviews/{orderId}/resolve` accepts organization, resolution, reason, expected concurrency version, and optional correlation ID. Resolutions are `confirm_void`, `resume_payment`, and `escalate`. Dedicated `order.payment-review.read`/`order.payment-review.resolve` authorization is mandatory. Each decision atomically advances concurrency, appends immutable history, updates Order when applicable, and publishes `order.payment-review-resolved.v1` plus `order.audit.v1`. Open review count and oldest age are exported as `order.payment_review.open` and `order.payment_review.oldest_age_seconds`. Migration 4 cannot be downgraded after any case/history exists; use forward recovery.

For release verification, inject disposable Order/Reporting database settings, a disposable PostgreSQL administrator connection, and an isolated RabbitMQ URI, then run `scripts/test-payment-review-operations.ps1` with its three explicit confirmation switches. The current 13-case matrix covers HTTP 404/403/409, history/permission probes and actor/decision attribution, competing-claim and expired-lease fencing, migration rollback/forward guards, Reporting-13 removal/replay, repository-produced required/resolved/audit payloads surviving a failed hosted dispatcher and publishing persistently after worker restart, hosted Reporting projection with inbox duplicate suppression, and firing/resolved delivery through the isolated Alertmanager receiver. Prior eight-case evidence remains historical. It does not certify a full broker-container restart, a production receiver, or a production threshold.

The Customer Portal consumes new GET `payment-reviews/branches/{branchId}/access` and `payment-reviews/{orderId}/history` routes under `/api/order/v1`, both with `organizationId` query context. The probe reports current read/resolve access, not a grant; history hides denied/cross-tenant cases with 404 and returns the most recent 100 migration-4 entries, newest first. Reads and mutations remain independently authorized, responses are no-store, and denial logs contain only permission codes under `nexaconnect-order`. No schema change is needed. See [operator API/UI contract and diagnostics](../../../docs/API/Payment-Review-Operator-UI.md).

Resolution claims use a two-minute PostgreSQL lease, advance the concurrency version, and carry an opaque fencing token. Active `resolving` cases are visible by direct read but omitted from the open list; after expiration they appear open and only the same resolution may take over. Final commit must match the fencing token, and the retained Authorization decision ID is written with history/event state. Failed dependency calls release the claim; a process loss relies on expiry. Confirm-void retries can repeat idempotent compensation by Order identity.

Resolution requests against a non-open case or stale expected version return 409 before side effects. The former non-open successful no-op response is no longer used; callers must inspect current case/history and make a new explicit decision only when actionable.

The service also exposes `POST` and `GET /api/order/v1/orders` for the aggregate slice, plus the public place-order workflow endpoint. Production provider credentials and migration execution remain operational follow-up work; the deployed Kitchen ticket create/cancel API is now part of the workflow boundary.

Customer Portal create, read, and workflow requests are revalidated inside Order: Platform Directory confirms organization access, Restaurant confirms branch ownership, and Authorization evaluates `order.create`, `order.read`, or `order.place`. Request organization IDs must match the protected context. Cross-tenant reads return `404`; commands fail before the workflow executes.

Structured logs use service name `nexaconnect-order`; correlation IDs propagate through tenant checks and registered workflow HTTP adapters.
JSON stdout is always enabled. Enable OTLP with `Observability__OtlpEnabled=true`; use the [observability guide](../../../docs/Deployment/Observability.md) for the endpoint and queries.

In PostgreSQL mode, the `nexaconnect-order` meter reports pending payment-reconciliation inbox work, the oldest expired processing lease, pending recoverable checkout workflows, oldest workflow recovery age, unpublished outbox count/age, and gauge-collection failures. Recovery attempts and failures are counters. A collection failure means prior gauge samples may be stale. `OperationalMetrics:PollInterval` defaults to 30 seconds. `WorkflowRecovery:PollInterval`, `LeaseDuration`, and `RetryDelay` default to 5, 30, and 15 seconds and must all be positive or startup fails. Enable `PaymentReconciliationConsumer` with the same secret-managed RabbitMQ connection after compatible Payment events are deployed. The instruments contain no tenant, order, payment, or message labels. RabbitMQ queue and dead-letter depth are exported by the broker's Prometheus plugin in the local stack.
