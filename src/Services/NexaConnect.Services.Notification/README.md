# Notification Service

Notification owns queued message state, delivery-facing provider adapters, integration-event consumption, product audit records, and its PostgreSQL inbox/outbox. Other services request notifications through the versioned `NotificationRequestedV1` integration contract; they do not reference Notification domain or persistence models.

## API and tenant boundary

- `POST /api/notification/v1/notifications` accepts `OrganizationId`, `Channel`, `Recipient`, `Subject`, and `Body`; public callers cannot set the internal source-event id. It requires an authenticated user, matching `X-Nexa-Organization-Id`, `X-Nexa-Application-Code: nexa_connect`, active tenant access, and `notification.send`. Workloads request notifications through `NotificationRequestedV1`, not this tenant route.
- `GET /api/notification/v1/notifications/{id}` requires `X-Nexa-Organization-Id`, `X-Nexa-Application-Code: nexa_connect`, and `notification.read`. PostgreSQL lookup is organization-leading so an ID cannot select another tenant's record.
- `GET /bff/customer/notifications/{id}` is the browser contract. Customer BFF derives both tenant headers from its protected tenant cookie and forwards the server-held access token.

Tenant access is revalidated through Platform Directory and Authorization. `tenant-admin` receives organization-scoped notification permissions. A `store-manager` permission remains restaurant-scoped and therefore does not satisfy this organization-only API.

## Durable integration mode

Set `Persistence__Provider=PostgreSQL`, `ConnectionStrings__Notification`, and secret-managed `Outbox__ConnectionString`. Migration 2 adds organization/source-event scoping, append-only notification audit records, a lease-based inbox, and the transactional outbox. Migration 3 adds leased provider delivery/reconciliation state and append-only attempt history. A successful insert atomically records `notification.queued`, `NotificationQueuedV1`, and `PlatformAuditEventV1`. Repeated `NotificationRequestedV1` delivery is safe: the inbox deduplicates by event/consumer and `notifications.source_event_id` supplies a second durable uniqueness boundary. Conflicting reuse, including another organization using the same event id, is rejected.

Enable the RabbitMQ consumer with `NotificationConsumer__Enabled=true`. Optional settings are `NotificationConsumer__Exchange` (default `nexaconnect.events`), `NotificationConsumer__Queue` (default `nexaconnect.notification.requested.v1`), and `NotificationConsumer__Prefetch` (default `16`). Permanent contract/JSON failures dead-letter using `notification.requested.v1.dead`; transient failures are requeued. Deploy migration 3 before enabling the current application.

## Provider delivery

Provider delivery is available only with PostgreSQL authoritative persistence. Set `NotificationDelivery__Enabled=true`, `NotificationProvider__BaseUrl`, secret-managed `NotificationProvider__ApiToken`, `NotificationProvider__ProviderCode`, and optional submit/receipt paths. Outside Development the provider URL must use HTTPS. The adapter sends `POST {Path}` with bearer authentication, `Idempotency-Key: {notificationId}`, the validated correlation header, and `{ clientReference, channel, recipient, subject, body }`. It polls `GET {ReceiptPath}`, replacing `{id}` with the provider receipt id or notification id. Successful JSON responses use `{ outcome, providerMessageId?, errorCategory?, retryAtUtc? }`, where outcome is `accepted`, `delivered`, `pending`, `transientFailure`, or `permanentFailure`.

The worker leases due rows with `SKIP LOCKED`. Submission follows `queued -> submitting -> provider_accepted`; receipt polling follows `provider_accepted -> reconciling -> delivered`. Transient submissions use bounded exponential retry, provider `Retry-After`/`retryAtUtc` is honored, and permanent or exhausted attempts become `delivery_failed`. Expired submit/reconcile leases are reclaimed with the same notification id so provider submission remains idempotent. `NotificationDelivery__MaximumAttempts` bounds submission and receipt attempts; `PollInterval` and `Lease` control worker cadence. Accepted, delivered, and failed transitions atomically append safe audit and `notification.delivery-status-changed.v1` outbox events. Webhooks are intentionally not exposed until a concrete provider supplies a signed callback contract.

Provider HTTP `408`, `429`, and `5xx` responses are transient; `400`/`422` are permanent request failures; other non-success responses are classified as provider authorization failures. Invalid provider responses are retried without logging their bodies. The in-memory adapter remains development-only and does not perform provider delivery.

For rollout, apply Notification migration 3 and Reporting migration 7, deploy delivery disabled, verify connectivity/telemetry, then enable the worker. For rollback, disable delivery and producers, allow active leases to expire, drain/stop the consumer and outbox dispatcher, roll back the application, downgrade Reporting 7, and downgrade Notification 3. The destructive downgrade removes attempt history and provider lifecycle columns but preserves migration-2 queued notifications/audit/inbox/outbox data.

Structured logs and OTLP use service name `nexaconnect-notification`. Logs include safe organization, permission, and correlation identifiers but never recipient, subject, body, provider responses, access tokens, or provider secrets. Useful Loki filters include `{service_name="nexaconnect-notification"} |= "Notification delivery processing failed"` and `{service_name="nexaconnect-notification"} |= "Notification authorization denied"`; alert on due/expired delivery leases, `delivery_failed` growth, queue/DLQ depth, unpublished outbox age, and inbox lease age.
