# NexaConnect Customer Portal

The [joined end-of-day gate](../../../../docs/Deployment/End-Of-Day-Portal-Acceptance.md) adds eight real-OIDC browser scenarios through actual BFF/Reporting/source APIs. Run `npm run test:end-of-day:guards` before the guarded launcher; `test:e2e:end-of-day:live` requires its complete generated environment. The existing synthetic end-of-day suite remains a separate UI contract check.

**End-of-day draft** is a read-only NexaConnect navigation page using branch UUID and completed branch-local date. The server supplies timezone and authoritative sales/tender/refund/drawer summaries, source observation times and unresolved/evidence issues. Reloads, filters, tenant changes and failures clear financial results; generation fencing discards late responses and the browser deadline is 40 seconds. Response scope, draft status, currency and net-sales arithmetic are validated before display. No settlement action, export, polling or repair is supplied. Run `npm run test:e2e:end-of-day` from `src/Frontend`; its six synthetic browser cases complement API/database tests. See [contract](../../../../docs/API/End-Of-Day-Draft.md).

The [joined financial acceptance runner](../../../../docs/Deployment/Financial-Completeness-Portal-Acceptance.md) exercises actual OIDC, tenant/permission boundaries, Reporting delivery and recorded status progression. Synthetic unit/browser contracts remain separate; provider and production acceptance are outside this harness.

**Sales reconciliation** uses `/bff/customer/reports/financial-completeness` alongside the existing sales read, with an administrator-supplied branch UUID and identical explicit closed UTC filters of at most 31 days. It displays Not checked, Gaps detected or Observed complete, check/source times and separate sales/payment/refund inventories. Observations are historical; fresh totals may differ after later projection changes. Reload/filter/tenant changes clear results and cancel pending reads; denial clears both results, while other reconciliation failures permit independently successful totals. The browser deadline is 25 seconds. No polling, reconciliation or repair is performed. Reporting 20 and a recorded check for that exact window are prerequisites; use privileged tooling to record one. Run `npm run test:e2e:financial-completeness`; see [contract](../../../../docs/API/Financial-Reporting-Completeness.md) and [browser evidence](../../../../docs/Architecture/Evidence/Financial-Completeness-Portal-Acceptance.md).

Dashboard and sales display gross sales, refunds and net sales using Reporting 18. Refunds belong to their refund UTC period, including older sales; net sales can be negative. Dashboard net paid retains the existing payment-fact measure. Latest global checkpoint is diagnostic only; receipt-backed sales/payment consumers are available through Reporting 19, but these screens do not certify complete accounting. See [semantics and deployment prerequisites](../../../../docs/API/Refund-Financial-Reporting.md).

Product configuration includes tax percentage and inclusive-menu-price controls alongside service charge. Rates allow two decimal places. Accepted orders retain their original policy; review existing service-charge settings before the pricing rollout. Cashier preview/confirmation is implemented in WPF POS. See [pricing contract and rollout](../../../../docs/API/Order-Pricing.md).

**Cash-close report** is a read-only single-store page: enter branch/store UUIDs and a UTC range of at most 31 days, then load 50-row pages. It shows currency, expected/counted/variance, review versions and capture/projection timestamps without totals or completeness claims. Reload is explicit; filter/tenant changes clear rows and failures remove the previous report. Current decisions stay in POS Cash Review. The BFF calls Reporting, which requires live POS access. Run `npm run test:e2e:cash-close`; see [contract and deployment prerequisites](../../../../docs/API/Cash-Close-Reporting.md).

The [joined Payment Review acceptance harness](../../e2e/payment-review-live/README.md) tests real OIDC/BFF/Order boundaries using operator-provisioned disposable accounts and marked fixtures. Run `npm run test:e2e:payment-review:live` only after supplying its documented settings; missing settings fail rather than skip. Existing synthetic browser tests remain separate.

Phase 8 provides the independently buildable tenant-scoped Customer Portal context/navigation shell. Authentication is owned by `NexaConnect.CustomerBff`; the browser receives only opaque cookies and selects one organization plus enabled product from `/bff/customer/access`. `/tenant` and `/features/*` revalidate the protected server-readable selection.

The portal includes profile, product switching, memberships, branches, configuration, Reporting dashboards/sales/activity preview, and Media-owned list/upload/original/variant download/delete. Uploads go directly to the signed S3-compatible URL and are completed through the BFF. Media verifies provider checksum/size, validates the image signature, scans with ClamAV, enforces pending-count and original-byte organization quotas, cleans expired sessions, and asynchronously creates thumbnail/display WebP variants. Generated variants are excluded from the original-byte quota and require separate bucket-capacity monitoring.

The organization-wide Branch and Media lists currently require an organization-scoped `tenant-admin` product assignment. A restaurant-scoped `store-manager` assignment does not satisfy those list decisions because the current list requests carry no restaurant filter.

The `nexa_connect` workspace includes Payment Reviews: enter an administrator-supplied branch UUID, inspect up to 100 actionable cases and the latest 100 immutable history entries, and use permission-aware decisions with required reason and confirmation. Branch UUID entry avoids requiring the organization-wide branch-list permission. Conflicts and ambiguous outcomes refresh authoritative state without automatically resubmitting; changing tenant clears the panel and aborts in-flight reads. Confirm void requires independent payment evidence and does not query a provider. See [the operator contract](../../../../docs/API/Payment-Review-Operator-UI.md). Run `npm run test:e2e:payment-review` for synthetic browser coverage; joined live identity/BFF/Order acceptance remains separate. Order must run independently of the Phase 8 launcher with migration 4 and its dependencies.

Run `npm run dev --workspace @nexaconnect/customer-portal` with `CUSTOMER_BFF_URL` set for local proxying. Run `npm run check`, `npm test`, and `npm run build --workspace @nexaconnect/customer-portal` from `src/Frontend`. Publishing the Customer BFF builds and embeds the SPA unless `SkipCustomerPortalBuild=true` is used after independently supplying verified assets.

For the same-origin Phase 8 development stack, trust the ASP.NET development certificate (`dotnet dev-certs https --trust`), start infrastructure with `docker compose up -d`, apply migrations 1-4 for Media and the current migrations for the other services, seed at least one organization-enabled Catalog product, build once, and run `scripts/run-phase8-development.ps1`. Pass `-Build` to build each application before launch. The script loads the ignored `.env`, rejects missing or placeholder secrets, forces ClamAV scanning on, enables PostgreSQL Catalog persistence and the RabbitMQ activity publishers/consumer, preserves separate Catalog and Media workload identities, starts Platform Directory, Authorization, Restaurant, Reporting, Media, Catalog, Customer BFF at `https://localhost:51829`, and Platform Admin BFF with its Product Owner Portal at `https://localhost:58627`, and waits only for bounded HTTP liveness before writing separate logs under `.runlogs/phase8`. Liveness does not prove Keycloak credentials, seed data, broker delivery, storage/CORS, scanner signatures, or tenant workflows; complete the authenticated functional smoke test afterward. It executes each built service DLL directly and records the exact service PID and start identity in ignored `.runstate/phase8`; `scripts/stop-phase8-development.ps1` validates and stops only those recorded service processes, including both portal BFFs, and retains state when cleanup is incomplete, while infrastructure containers remain running. Scanner-disabled development requires a separate manual Media launch.

After the stack and seed data are ready, run the opt-in [joined Playwright acceptance suite](../../e2e/phase8/README.md). The suite uses environment-provided customer credentials and identifiers and tests the browser-to-provider Media lifecycle; implementing the harness does not replace the required environment-specific execution, recovery, load, TLS, CORS, credential, or operational validation.

The NexaConnect workspace includes **Kitchen queue**: enter a branch UUID and optional station code, page through active tickets, and use permission-aware Start/Ready/Complete actions. The current 50-ticket page refreshes every ten seconds; manual refresh resets to page one. Actions lock during requests or stale state. Conflicts/timeouts trigger authoritative reads with no automatic mutation replay; branch/station/tenant changes clear the queue. Kitchen completion does not confirm payment. Configure BFF `Services__Kitchen`; the Phase 8 launcher does not start Kitchen. Run `npm run test:e2e:kitchen` for synthetic browser contracts. See [Kitchen behavior and release gates](../../../../docs/API/Kitchen-Queue.md).
