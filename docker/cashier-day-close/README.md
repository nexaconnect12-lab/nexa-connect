# Disposable cashier-to-day-close infrastructure

The Slice 5 historical cashier-cutoff launcher supplies Order `Services:POS` for strict terminal admission and both host environment variables explicitly. The test-only fixture accepts Singapore or Bangkok business calendars; production binaries receive no clock override. Current cutoff acceptance requires eighteen browser cases plus six Authorization persistence cases. See [manager guide](../../docs/Deployment/First-Draft-Manager.md).

RabbitMQ probes run as its broker user (`gosu rabbitmq rabbitmq-diagnostics`) to avoid a root probe creating an inaccessible Erlang cookie during server startup. The [owned local draft topology](../first-draft/README.md) extends this template with persistent generated volumes; the disposable cashier acceptance lifecycle still removes its own resources.

If generated infrastructure startup fails, the shared launcher records only a bounded RabbitMQ startup diagnostic before cleanup: exit/running/OOM state and an allow-listed category. It verifies the generated project's ownership label and never publishes raw container logs or secrets. Read the retained `verification.json` and [CI follow-up](../../docs/Deployment/CI-Clean-Checkout-Verification.md); startup failure still fails the gate and does not trigger automatic retry.

Audited settlement replay is implemented in POS 23 / Reporting 22 at compatibility 0.38.0. Administrative --settlements preview pins original V1/V2 payloads; execute records intent in the same source snapshot, append-only attempts and actual database-login attribution before/after broker calls. Original receipts, source revisions and dispatcher flags stay unchanged. No customer replay endpoint or grant is added. See [ADR-035](../../docs/Architecture/Decisions/ADR-035-audited-settlement-replay.md), [command](../../docs/API/Settlement-Replay.md) and [operations](../../docs/Deployment/Settlement-Replay.md).

Settlement reporting now uses Reporting 22 / POS 23 with matching binaries at compatibility 0.38.0. New commits atomically publish V2 proof; the opt-in consumer accepts original V1/V2, stores immutable facts/hash receipts and exposes a live authorized business-date ledger with separate corrections and delivery gaps. V1 proof remains unavailable rather than enriched. No new financial authority is added. See [ADR-034](../../docs/Architecture/Decisions/ADR-034-settlement-reporting.md), [API](../../docs/API/Settlement-Reporting.md) and [rollout](../../docs/Deployment/Settlement-Reporting.md).

Current cutoff/correction gate targets POS 23 / Reporting 22 at 0.38.0. Run-owned start-pos-held-publication pauses only its dispatcher batch; source correction capture/comparison is checked missing then matched after original dispatch. Six strictly enumerated child actions are accepted only in cutoff mode; production hosts expose no control route. See [contract](../../docs/API/Correction-Day-Evidence.md) and [operations](../../docs/Deployment/Correction-Day-Evidence.md).

The current cutoff/correction acceptance mode deploys POS 23 / Reporting 22 at compatibility 0.38.0 with opt-in correction consumer enabled. Its genuine posted correction is checked through Reporting/BFF and the portal; other older gate targets remain historical. See [contract](../../docs/API/Cash-Correction-Reporting.md) and [operations](../../docs/Deployment/Cash-Correction-Reporting.md).

Current cutoff/approval/settlement/correction mode uses Order 19 / Payment 18 / POS 23 / Authorization 15 and compatibility 0.38.0. It requires eighteen distinct real-OIDC browser passes, including temporary source fence preparation/cancellation and durable settlement receipt/replay/restart with workload-only source decisions. Six Authorization persistence cases and exact cleanup remain required. Current correction Reporting execution is recorded in [Reporting evidence](../../docs/Architecture/Evidence/Cash-Correction-Reporting-Acceptance.md); [posting evidence](../../docs/Architecture/Evidence/Late-Cash-Correction-Acceptance.md) preserves the preceding POS-20 run; previous settlement/preparation runs remain historical. The additional scenario verifies populated late-work review, source-verified cash correction, mandatory live amount limits and response-loss/restart recovery. Original non-cutoff modes retain their schema targets.

The preceding cutoff-only mode used source revision protocol 2 (Order 13 / Payment 12 / POS 10, compatibility 0.26.0) and required exact-set Reporting delivery proof. Prior 0.25.0 acceptance records remain historical. The original non-cutoff cashier/preparation modes retain their pinned schemas. Revision-only execution remains historical; current seal execution is recorded separately under docs/Architecture/Evidence/Day-Close-Seals.md.

The [joined cashier-to-cutoff launcher](../../docs/Deployment/Cashier-Day-Cutoff-Acceptance.md) reuses this ten-context topology under its own generated project and newer schema targets. It adds an optional generated accountant password to the disposable Keycloak environment; existing launchers default that unused setting. No production topology/permission change is introduced.

Use [the guarded cashier-to-day-close launcher](../../scripts/test-cashier-day-close.ps1) or [the cutoff launcher](../../scripts/test-cashier-day-cutoff.ps1) with `-ConfirmDisposableInfrastructure`. This dedicated topology provisions ten application databases/runtime roles (Platform Directory, Restaurant, Authorization, Catalog, Inventory, Kitchen, Order, Payment, POS and Reporting), a separate Keycloak database and RabbitMQ. PostgreSQL 17 uses tmpfs, Keycloak 26.7.0 imports the generated realm, and RabbitMQ 4 carries actual Order publications. All published listeners bind to IPv4 loopback; run-owned credentials and identities are generated and removed with the exact project.

The shared launcher starts ten service APIs and one published Customer BFF. Order and POS use the acceptance-only real-entry-point clock host; the other service hosts retain normal system clocks. Reference setup creates no financial/state-transition records. See [commands, clock boundary, evidence and cleanup](../../docs/Deployment/Cashier-Day-Close-Acceptance.md). This is disposable acceptance infrastructure, not a production deployment or midnight certification.
